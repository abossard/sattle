# Sattle canvas

Graph display and projection editor for the Sattle design in `../brainstorm`, on top of the engine in `../engine`. A React 19 and Fluent UI v9 shell with one Zustand store around a WebGL2 graph view (100k nodes and 300k edges at 60 fps, see `PERF.md`).

## Run

- `npm install`
- `npm run dev` (starts Vite). `ENGINE_PORT=5091 npm run dev` points the `/engine` proxy at another engine port (default 5080).
- `npm run build` (type check plus production build in `dist/`)
- `npm test`: 930 parametrized unit and component tests, including axe on every view and dialog in jsdom. `tests/defects` holds one test per defect of the code review (`paper/research/07-code-review-findings.md`) that was fixed; each failed for the reason the review gives until its fix.
- `npm run a11y` (dev server or `vite preview` running on `http://localhost:5173/` unless a base URL is given, engine on the proxied port; it stops with a clear message when the app does not start): axe-core with color contrast on every view, theme and dialog in real Chrome, plus keyboard-only walkthroughs with real key events. `A11Y_SOURCE` and `A11Y_ENGINE` select the sources. Three checks need the estate engine and skip with a note otherwise: the document view (an engine that serves a document graph) and the value roles of the `health` graph (`A11Y_ROLES_GRAPH`) in each theme: no coloring is chosen, a real screenshot of the canvas must contain pixels of every role color of the legend, every element of a type that carries a hinted property must have a role, and the legend in the panel must name each role.
- `npm run walkthroughs` (app on `http://localhost:5173/` unless a base URL is given, then walkthrough names to run only some): replays `tests/walkthroughs/*.json` in real Chrome against the engine behind the proxy and checks them (see "Building every operator in the editor"); exit 1 on a mismatch, 2 when nothing ran. It starts by printing the engine it runs against (space, protocol, kernel digest, catalog revision, sequence number, input; the engine reports no build number, so the kernel digest and catalog revision are what identify it). Run it when the engine, the editor commands or a walkthrough changed. It takes minutes: each command is a round trip to the engine (about a second).
- `npm run sync-palette [engine-url]`: writes the engine's `GET /palette` to `tests/fixtures/palette.json`; `tests/slot-kinds.test.ts` reads every slot kind of every operator from it, so a slot the panel cannot edit fails the test after the next sync. Run it when the engine's kernel changed (a new operator, slot or parameter) and commit the file; `npm test` never fetches it, so without a sync the test only knows the last synced palette.
- `npm run document-live` (app and an engine that plays a capture slowly, e.g. `sattle serve lab/fixtures --speed 2`): opens the page once, shows the first document graph and checks that it passed through more than one revision without a reload and ends at the revision and digest `GET /graphs/{g}/document` answers; exit 2 when it could not see a live update. Run it when the document view, the event stream or the engine's document endpoint changed, not on every build: it takes minutes and needs a slow engine; `npm run a11y` covers the document view on a settled engine.
- `npm run perf` after `npx vite preview --port 4173`: headless Chrome load and frame-rate harness, see `PERF.md`.
- `npm run demo` runs the engine's built Release binaries in place (`engine/src/Sattle.Cli/bin/Release/net10.0`) on the synthetic estate fixture (`replay --out`) and writes its output to `public/demo/estate`, the default source of the app. It never builds `engine/`: it stops with a message when the binaries are missing or older than the engine's sources (`ENGINE_DLL=path/to/sattle.dll` names other binaries; `npm run demo -- --build` builds with `dotnet run`, only on request). It refuses to write when a graph that should have edges (the master, the service tree, capabilities, deployment health and the health graphs) has none. Run it when the engine's definitions or the fixture change and commit the result; nothing in the directory is edited by hand. It holds, per graph, the ontology, the snapshots, the patches, the lineage in both directions and, for the report, the rendered document; the telemetry per graph (`NAME.meters.json`, `NAME.telemetry.ndjson`) and the references (`NAME.references.ndjson`).
- Source and view in the URL: `#source=engine&view=editor`. The hash and the store follow each other both ways (typing a hash, links, back and forward; a hash with only one part changes only that part). Sources: `engine`, `demo`, `demo-stream`, `repo`, `synth-small`, `synth-medium`, `synth-100k`, `synth-100k-stream`. Views: `data`, `space`, `editor`, `ontology`.
- Against the engine: `dotnet build -c Release engine/src/Sattle.Cli`, then `dotnet engine/src/Sattle.Cli/bin/Release/net10.0/sattle.dll serve lab/fixtures --port 5080`, then `npm run dev` and open `#source=engine`. `?engine=URL` selects another base.

## Shell, state and caching

- Fluent v9 components and tokens everywhere (Toolbar, TabList, Tree, DataGrid, Accordion, Dialog, Menu, Select, Combobox, MessageBar, Slider, ...), themes `webLightTheme`, `webDarkTheme` and `teamsHighContrastTheme`, focus handling by Fluent's focus manager. Custom drawing is limited to the WebGL view (`CanvasHost` mounts it and gets out of the way) and the editor's SVG node canvas.
- One Zustand store (`src/state/store.ts`) with Redux-style actions (`types.ts`) and a pure reducer (`reducer.ts`). State is plain and serializable: summaries and UI state, never graphs. The mutable side (workspace, histories, GL panes, telemetry stores, the draft session) lives in `runtime.ts`.
- `dispatch(action)` runs the effects (`effects.ts`, `editor-effects.ts`) in order, then the reducer. Every server push becomes an action (`feed/patch`, `feed/telemetry`, `feed/telemetryReset`, `feed/resync`, `feed/connection`, `feed/rejected`) and is applied to the runtime in the order it arrives. Patches and telemetry frames do not change the state themselves: effects report throttled summaries (`data/summary` at most every 100 ms, time at most every 250 ms), so frames never render React components.
- Components are functional and select the smallest slice they need; data-dependent panels select a per-graph `version` counter and read the runtime.
- Caching (protocol v3): history is read from revision-addressed immutable URLs (`snapshot?revision=0`, `patches?after=a&to=head`), which the engine sends as `immutable` with ETags, so the browser's HTTP cache serves them on reload (measured: `transferSize` 0, `deliveryType: cache`); head resources revalidate with `If-None-Match` and answer 304. No IndexedDB: the HTTP cache needs no code.
- Resume: the sequence number is read before the history; the stream subscribes with `after = seq` and resumes after the last sequence number seen when the connection returns. Duplicates are dropped by revision (patches) and window time (telemetry). The shell shows "stale" while disconnected and "resynchronizing" after a gap.

## Views

- Data graph: filters, search, neighbourhood focus, groups, layout, timeline, telemetry, inspector. The left panel has a second tab, Elements: the same graph as a Fluent DataGrid (nodes or edges, filterable, selection synced both ways, 300 rows shown with the selected row always present), and the inspector lists connections as a Tree that navigates with Enter. This is the keyboard and screen reader alternative to the canvas, and the only view when WebGL2 is missing.
- Graph space: all graphs side by side or stacked on one time axis, shared identity and lineage highlights.
- Projection editor: see below.
- Node labels use the `name` property, or a property whose id ends in `.name` (module-qualified, such as `acme.health.name`), else the id.
- Color by property, for nodes and for edges, each with its own control and legend (Filters, "Color by property"). Nodes or edges take the color of one property's value; the legend lists value, count and, when there is a hint, the role with its glyph and word. Labels carry the value and the role glyph (`✓ ⚠ ✖ ?`), danger edges are dashed, and the Elements list gets a column with the value and the role word, so color is never the only cue. Colors follow patches and the timeline: a patch that changes the property recolors the element, a value the legend has not seen rebuilds it, and moving the time slider shows the state at that revision (legend counts included).
- The default source is the engine's output on the synthetic estate (static files, `npm run demo`): the master and each projection with its edges (pods and flows, services with lifted call edges, capabilities with edges lifted again, deployment health, the health graphs, the report as a document). The graph space view shows all of them side by side.
- Tree (engine 3.14 marks, form agreed with the engine session; built on a hand-made graph, `tests/fixtures/tree-graph.ts`, and checked on the engine's `healthTree` (21 elements on the estate, 504 on the newest capture); a graph whose ontology shares the marks but holds none of the tree types does not get the tab): a graph whose ontology marks a hierarchy opens with the tabs Tree and Graph, Tree first (`src/ui/TreeView.tsx`, model in `src/app/tree-model.ts`, nothing keyed on a name). The ontology marks the hierarchy relationship type (`hierarchy: true` on the type, parent is the source), the other relationship types are read from its structure (both ends in the tree types: a link between nodes; an end outside them, such as evidence or a signal: support), and per entity type `treeState` names the properties of its own state, rolled-up state, severity, kind (what the row says it is) and count of descendants per state value, plus the optional `curatedBy`, `critical`, `hidden`, `mode` and `share` of authored curation (the property ids come from the ontology; the engine serves them as `nodeKind`, `ownState`, `rolledState`, `rolledSeverity`, the three counts, `critical`, `hidden`, `curatedBy`, `rollupMode` and `rollupShare`). Curated rows carry a badge and the record, critical rows a badge, hidden elements are left out with their subtree behind "Show hidden", and "Why this state" names the roll-up policy; curation is read only, the engine has no write path. Until the engine marks the hierarchy, `src/source/tree-standin.ts` (a local stand-in, keyed by the ontology `acme.health`, to be removed) lets the committed estate output open its `health` graph as a tree on `acme.health.Contains`; an ontology that carries the marker never uses it; value roles say what each state value means. Each row (Fluent `FlatTree`, only the rows in view are rendered) shows the element, its type, its rolled-up state and, when it means something and differs, its own state (glyph and word, never color alone), its descendants by state (the engine's counts, otherwise its direct children; `⚠3`), the number of supporting elements and of links, and `Δ` when the row changed in the revision the timeline shows. It opens on the paths to the nodes where something is wrong (a warning or a danger), with a switch "Only where something is wrong", children sorted worst first or by name, "Expand below selected" (also `*`), "Collapse all", "Open paths to problems" and a search that opens the path to each match. A click or Enter selects the row (the shared selection: the graph view and the Inspector follow); the chevron and the arrow keys open and close. The keyboard works over the whole list, also for rows that are not rendered: arrows, Home, End, PageUp, PageDown, Left to close or go to the parent, Right to open or enter, type-ahead; a row is named by its content, so what is drawn and what is read cannot differ (WCAG 2.5.3): glyphs are drawn and hidden from readers, the words and role of each state stand for them, and level and position come from the tree. The Inspector adds "Why this state": own and rolled-up state, the children that drive the roll-up, the supporting elements with their properties, and the links; the lineage down to the master is the section after it.
- Abstraction (engine 3.11 lineage): selecting an element highlights what it stands for below it and what it is part of above it, in every graph. Forward lineage is followed level by level down to the master (a lifted edge names all the lower edges and nodes it aggregates), reverse lineage up from the master (what a master node is part of); nodes get a dashed ring for what is below and a pink ring for what is above, edges are drawn in the pink identity color. At most 400 lookups per selection. Where the engine's lineage is partial (an element emitted from a windowed `Group`, `Rollup`, `Threshold` or `Series` has only its group key; a graph reading through an aggregate is listed in `incompleteIn`) the Inspector says so instead of presenting the highlight as complete.
- References (engine 3.11): a relationship that names an endpoint the graph does not hold is drawn to a stub node, hollow with a dashed outline, labelled from the identity key the engine reports (`◌ cluster / namespace / name`), typed `<entity type> (reference)` so the Types filter can hide them, with dashed edges. The Inspector says why it is missing: `absent` (no graph holds it), or in which other graph, with a link that opens it there. The reasons are read alone when the graph is first shown (engine 3.12: `GET /graphs/{g}/references`, paged by id; static output: `NAME.references.ndjson`); snapshots are asked for with `references=false`. The stubs are named generically until they arrive and for a source that gives none. At most 5000 stubs per graph; the status line counts edges beyond that as not drawn. The entity that arrives takes over its stub's place.
- Supporting elements: by default a graph whose ontology has value roles collapses the elements that only support others onto the node they support (count badge, double-click or Space to expand, "Expand all" in Filters, Groups). Which elements: a relationship type whose one end has no property with roles and whose other end has (`supportRelation`), so evidence of a component collapses and components and signals stay; no name is involved, and a graph without roles collapses nothing. "Groups" offers it as "Supporting elements" beside any relationship type.
- A projection graph with nodes, no edges and relationship types declared by its ontology shows a notice on its canvas (`edgelessNotice`) saying it holds no edges, so the missing lines are not mistaken for a rendering fault.
- Value roles (engine 3.2): each property entry of the ontology may carry `presentation: [{ value, role }]` with the roles `ok`, `warning`, `danger`, `unknown`, `neutral`. When a graph's ontology has roles for a property of nodes (or of edges), that property colors them by default, the roles map to Fluent status tokens (`colorStatusSuccessForeground1` and the warning and danger ones; `colorNeutralForeground2` and `3` for neutral and unknown) of the light or dark theme for the canvas and of the active theme for the legend, and the user overrides per graph: another property, or type colors. When a target has roles for several properties (the `health` graph: `Component.state`, `Signal.degraded`, `Signal.unhealthy`) the default keeps all of them: an element takes the worst role (danger, warning, unknown, ok, neutral) among the hinted properties it has, its text names the property (`state: Healthy`), and the legend and the element list say so. A value without a role is neutral; in high contrast the glyph (`✓ ⚠ ✖ ? ○`) and word carry the role. `src/source/presentation.ts` reads exactly that shape and removes it from the ontology before schema validation (the contract schema forbids extra fields). Roles are also edited: the Definitions tab, "Value roles", gives a value of a property a role as a `ValueRole` node in the property's `presentation` slot.
- Ontology: types as a Fluent Tree beside the ontology drawn as a graph; for the engine, the module's catalog ontology and its text.

## Projection editor (engine source)

An edit session is a **draft** on the engine (`POST /drafts`), the browser keeps its own copy of the draft's catalog graph.

- Palette from `GET /palette` (kernel metadata, immutable per kernel digest): operators grouped by role with ports, parameters and slots; operators the engine cannot evaluate are listed disabled with the engine's reason. Add by clicking, from the quick-add list (`A`, type to filter) or the toolbar. New operators come from `POST /palette/skeleton` (kernel-fixed ports and defaults).
- Node canvas (SVG): cards with ports and wires laid out left to right by data flow, drag to move, marquee and Shift-click multi-select, drag from an output port to an input with live type checking (green inputs accept, dimmed ones do not), comments and groups, align and stack, zoom. Layout positions, comments and groups are the author's and live in `localStorage` per projection, not in the catalog. The Outline tab lists the same projection as a tree.
- Wiring is type checked (`commands.canWire`): an output or a projection input binding feeds an operator input, kinds match (`rows` or `graph`), one wire per input, no self loop, no cycle. The reason is announced and shown.
- Property panel from the palette: parameters by kind (select for enumerations, integer and decimal validated), expression slots from a text expression (`src/editor/expr.ts`: paths, literals, calls, infix, `id domain(component: expr)`), named assignments and aggregates, set properties, pattern nodes and edges, read fields, emitted type, connections (add and remove with only valid targets enabled), rules with direction class.
- Edits are catalog patches applied to the draft (`POST /drafts/{id}/patches` with the draft revision as expected revision, guards = before states). The engine answers diagnostics by element id, shown on the card (✖ or ⚠), in the Problems tab and in the panel; the draft is printable and committable only without errors.
- New projection (toolbar): name, output ontology, graph inputs (port, the space graph that feeds it, the ontology it expects), parameters (name, kind, value bound in the space) and the graph it produces; the catalog gets the projection, its ports, the space graph and one binding per port. Operators are then added in the graph editor. Function names in expressions may use the text spelling (`concat`, `lowerInvariant`, `if`) or the palette spelling.
- Module definitions (the Definitions tab): row types with fields (kind from the palette's value kinds, optional or required), constraints (acyclic, cardinality, enum, pattern), equivalence policies (name, mode, threshold, two identity domains in order). A Link-like operator (the palette slots `left` and `right` take identities) gets a policy selector. The slots, node types, parameters, constraint kinds (key, enum, range, pattern, cardinality, acyclic, each with the parts it uses), equivalence modes, field value kinds, rule parameters and value roles all come from `/palette` (engine 3.2: `declarations`, `rowTypes`, `equivalencePolicies`, `rules`, `valueRoles`, `valueRoleSlot`); an engine that does not describe them gets a message, not a guess. Only the names of the relationships that connect the parts (`constrains`, `onProperty`, `between`, `createKey`, `governs`, `valueKind`) are written in `src/editor/structures.ts`.
- Rule programs from the palette: class, reason, the rule parameters the class defines or its policies set (`putput`, `accept`, `onDelete`, typed and constrained by `rules.params`), create key, defaults on create and sets on delete, the other rule slots (`node`, `edge`, `id`, `equate`, `keep`) with the same slot editors as operators, and what the rule governs. Nothing is keyed on an operator or class name: slots, parameters and policies come from `/palette`, and a slot kind the editor cannot build (for example Fixpoint's relation) shows its kinds and points to the Text tab.
- Parameter bindings: select a parameter port of a projection and edit the literal each graph of the space binds to it (`Binding.value`, typed by the port's value kind); the text shows `minReady: 4` in the space.
- Region selection by keyboard: `M` starts a region at the selected operator, arrows resize it (Shift: fine steps), Enter selects everything it touches, Escape cancels; each step is announced.
- Text and graph stay in sync both ways: the Text tab shows the module as the engine prints it (`modules[m].text` of every answer); editing it sends `POST /check`, and the difference between the draft graph and the parsed text becomes one draft patch (one undo step).
- Undo and redo: 99 steps, as inverse edits applied to the draft (never a rewind). Redo is cleared by a new edit.
- Versions: releases of the module (`GET /releases`), open the text of a release, compare two releases (patch summary), restore a release into the draft (an ordinary draft patch, read back from the draft's log so it can be undone). Commit (`Ctrl+S`) names the module version in its header before committing; the engine's answer decides.
- Preview (`POST /drafts/{id}/preview`): counts, scope stated (rows evaluated, complete or partial), diff against the live graphs when complete, and the previewed graph drawn on a canvas. The live engine is untouched.
- Refactoring: select operators or rules and move them into a new projection (extract), inline a projection, move a rule. The engine plans a patch (`POST /drafts/{id}/refactor`), the dialog shows its size and the preserved-union note first, Apply adds it to the draft as one undoable step. Engine refusals (`SharedOperator`, `DependsOnUnmoved`, ...) are shown as they come.
- Keyboard (`?` lists all): arrows select the next operator, Shift+arrows move (Alt: fine), Enter edits properties, `W` then arrows and Enter connects the selected output, `A` adds, Delete removes, Ctrl+C, V, D copy, paste, duplicate, Ctrl+A, Ctrl+Z, Ctrl+Shift+Z, Ctrl+G refactor, Ctrl+S commit, Escape.

## Building every operator in the editor

Each walkthrough is a list of editor commands (`tests/walkthroughs/*.json`: module, the projection it rebuilds, the commands, and for some the same projection written as text) sent through `editor/do` to a draft on the engine, with the Text tab never used. The JSON files are the source; `npm run walkthroughs` checks each: every command is accepted, the engine reports no diagnostics (beyond those a file allows), the projection it rebuilds prints the same canonical text and previews with the same digest, and a projection written as text (`text`, applied through the Text path into a twin projection) prints the same canonical text and previews with the same digest as the one the commands built. `nonEmpty` and `atLeast` files must also preview with entities or relationships (at least that many), so equal digests are not two empty graphs; `link-policy` has no graph output to count (a Link's equivalence is not an element of its graph), so it asserts the identity effect the engine reports with a preview (3.7): at least one more merged identity than the live space. The preview panel shows that effect (new identities, keys bound by a Link, merges, refused links; preview, live and the difference) under the output graphs. Which engine: the synthetic `estate` fixture, which has data for every operator (`sattle serve engine/tests/Sattle.Tests/fixtures/estate --cluster synth`). On any other engine pass `--allow-empty` (or `WALK_ALLOW_EMPTY=1`): text and digest checks stay, missing data is only noted. A real capture (`serve latest`, not in the repo) passed 8 of 8 that way, with equal digests for the health roll-up.

- Lift (engine 3.13): a card with two graph inputs (`edges`, `map`) and the relation as output, listed under "Lift to a higher level". Everything it shows comes from `/palette`: the parameters with their defaults (`within` starts at 24h, `selfLoops` at `drop`, `images` has none and is "(not set)", which means the mapping must be a function), the three relationship types (`ofType`, `liftEdge`, `liftVia`, chosen from the relationship types of the catalog), and the slots with their child types: `carry` and `keep` take a field (`keep` only `src.` or `dst.`, `carry` a property of the lower type), `derive` and `when` an expression, `state` a `LiftState` with its nine parameters edited as fields. The card names the types and shows only what differs from the defaults; an unfinished lift is listed with what it misses. - Fixpoint reads as a loop: a dotted region around the fixpoint and the operators between its `out` and the step result, a dashed arc for the `over` result, and the loop is selected with `L` or the "Select the loop" button; the result port is set in the References section of the panel.
- Declared parameters with defaults (`in minReady: param Integer = 0;`) show on the canvas as port lines and in the panel, a graph of the space binds them (`Binding.value`), and the new projection dialog takes `rows` inputs (row type, source), parameter defaults, purpose and retained revisions. With `minReady` set to 1 on `deploymentHealth` the preview's states change.
- No slot of any operator points at the Text tab: `Fixpoint.relation` (inferred from the input) says so and `Fixpoint.op` lists the step operators with "Select the loop"; `tests/slot-kinds.test.ts` reads every slot kind of the palette against the kinds the panel edits.
- Text applied over a draft that already holds graph edits keeps them: the edited module is replaced by its text, the modules it only affects (import pins) get the check patch's edits rebased on the draft. Before, applying a module's text removed the space graph and bindings of a projection built in the editor.
- Problems that name only the projection lead with the operators the editor knows to be incomplete (a required slot without a child, a missing required parameter, an unset type, an unconnected input), each as a card flag too.

## Five notations on one draft (`src/editing`, `src/editors`)

Five editors for a projection that share one core and one draft. Research, design choices and measured numbers: `paper/research/09-visual-editors.md` (section 9).

- **In the application**: the editor view has two ways to show a projection, `Canvas` (the node canvas, the default) and `Notations` (`src/editors/Notations.tsx`). A gesture is the action `editor/gesture`; the editor effects compose it on a copy of the draft and send it through the session, so it is one patch and one undo step, and the toolbar, the properties panel, problems, text, preview and commit work as before. "By example" picks from the graphs the projection's inputs are bound to, drawn by the data canvas.
- **On a page of their own**, over a draft in memory and the catalog of the synthetic estate: start the dev server and open `/tests/editors/page/index.html` (`?on=structure|pipeline|blocks|graph|example`, `?theme=light|dark|contrast`, `?grow=96` for about 500 operators, `?kinds` for statement kinds).
- **Core** (`src/editing`, pure): `doc.ts` reads a projection as row sets, steps, slots and entries from the definition graph and the palette, naming no operator kind; `exprtext.ts` prints an expression as the text `parseExpr` reads; `gestures.ts` composes what an author does (add, remove, move a step, rename, connect, add an entry, a match from picked data) into one patch on a scratch copy of the draft; `plan.ts` turns the application's `Command` into edits; `scope.ts` says what a hole can hold; `draft.ts` is the draft an editor works on (`session-draft.ts`: the engine session as one).
- **Views** (`src/editors`): `rows.ts` is a projection as rows, each with what it can become, as data; `parts.tsx` the inline editor of a row (Enter commits, Escape cancels). The notations draw and reach the rows differently and hold no draft state:
  - Structure: the outline of the whole projection, close to the canonical text. Arrow keys, Enter or F2 edits, Delete removes. Rows are windowed.
  - Steps: one row set at a time, a card per step. It says that the engine returns no rows per step.
  - Blocks: a palette by role and a stack per row set. A block is picked up (click, Enter or drag) and put down on a place that takes it; only those places are shown. Alt+Up and Alt+Down move a step, Escape lets go.
  - Wires: cards and wires laid out by data flow, nothing to arrange. A wire is an output, then an input (click, Enter or drag); inputs that cannot take it are disabled. Arrow keys move along wires and columns, Delete on an input disconnects. Only what is in view is mounted.
  - By example: pick entities of the data a projection reads, grow the example along their relationships, and add the pattern as a row set; a property becomes a condition only on request.
- **Statement kinds** (`src/editing/statements.ts`, a local stand-in, marked as one in the interface): a row set becomes a kind of step with a template (an ordinary projection, edited in the same notations) and parameters; the palette is rendered from the declarations; a use is lowered to the operators of its template before anything is sent to the engine. The file ends with what the engine has to provide for this to be real.

## Authoring a computed attribute end to end

Built once through the editor (the same commands the UI sends) against the engine on the latest real capture (66 pods, 15 services, 0 text steps): module `acme.healthmodel`, projection `podReady`, output ontology `acme.health`.

1. New projection: input `master` (graph, ontology `acme.ops`), parameter `minReady` (Integer, bound to 1), graph `podReady`.
2. Match: pattern nodes `p: infra.Pod`, `s: infra.Service`, edge `p -[infra.Backs]-> s`; wire `master` to its graph port.
3. Group: delete the placeholder key, keys `cluster`, `namespace`, `name` (`s.cluster`, ...), aggregate `ready` = `sum` of `If(coalesce(p.phase, "") == "Running", 1, 0)`; wire Match to it.
4. EmitEntity (create) of `health.Component`: identity `id component(id: concat("svc/", cluster, "/", namespace, "/", name))`, sets `key`, `kind`, `name`, `state = If(ready > minReady, "Healthy", "Unhealthy")`; wire Group to it.
5. The engine printed `projection podReady view forward output health { in master: graph ops; in minReady: param Integer; ... }` with zero problems; Preview: 13 components in 350 ms (partial scope, 500,824 of 579,175 rows), 7 Healthy and 6 Unhealthy; commit: catalog revision 14, the graph `podReady` appears in the space with 13 nodes.

Steps that needed the Text tab: none. What the engine's checker taught on the way (all fixed in the graph editor): an optional property in a comparison needs `coalesce`; a property read after a group must be a group key (`s.cluster` after grouping is an error); a create emit must set every required property; a new Group comes with placeholders to delete. Before this turn a new projection and a space graph could only be made in text.

## Telemetry

The graph carries data as well as structure. Telemetry is time-indexed, high rate and does not create revisions.

- Seam: `TelemetryBatch` (columnar: graph, tick, target `node` or `edge`, property, optional ids, `Float32Array` values). Dense batches (ids omitted) hold one value per element of the initial snapshot in snapshot order, which is how 300k edge values per tick travel; sparse batches carry element ids and update on top of the previous tick (also for elements added after the snapshot).
- Sources declare `Meter`s (property id, target, label, unit, range, optional warning threshold, `sqrt` scale for heavy-tailed rates) and default channel mappings. A source offers either a pull `TelemetryFeed` (static file, synthetic generator, simulated stream) or pushes `telemetry` stream events (a live engine source). Telemetry files are NDJSON, one sparse batch per line, validated line by line; bad lines are rejected visibly like every other record.
- Synthetic estate: request rate, error rate and latency on every edge, CPU and memory on every node, with a deterministic incident (first cluster and its callers: errors, latency and CPU rise from tick 10, recover by tick 50). Values are generated in a Web Worker as a pure function of (element, tick), so any tick can be regenerated.
- Time: one axis for the whole graph space, in seconds. Telemetry frames sit at their window start; revisions sit at their commit time when the source gives one (`Patch.time`, the `time` field of a patch stream event) and otherwise are placed by order on the telemetry windows, which the timeline says ("revisions placed by order", "some revisions placed by order" when history has none and live patches have). Moving the slider moves every graph to the revision and the telemetry window valid at that instant. The synthetic and demo sources have no commit times and place revision k at window k; the simulated stream delivers window k together with patch k and can keep producing windows after the last patch. Telemetry windows are keyed by time, so a revised (late) window updates its frame in place.
- Storage: 8-bit quantized frames per metric in a ring of the last 61 ticks (241 for small graphs), indexed by slot. 8 bits is the GPU format, so a frame is uploaded as it is; error is under 0.4% of each metric's range.
- Rendering: three byte channels per target are GPU attributes updated without layout work or instance rebuilds. Edges: width, flow pulse speed, state. Nodes: ring gauge, size, state. Each channel has a selectable metric; thresholds are editable.
- Non-color cues: width and pulse speed carry the rate; at or above the threshold an edge turns coral and dashed, a node gets a thicker segmented ring, a larger size and a `!` mark. At overview zoom the ring is too small to draw, so only the size cue and tint remain.
- Level of detail: pulses animate only when edges are long enough on screen and fewer than about 40k are visible (otherwise the view stays idle between ticks); while moving or animating, edge density adapts to the frame time.
- Inspector: a sparkline per metric of the selected element over the stored window with the threshold line and the current tick marked; tooltips show current values.
- Derived graphs carry their own telemetry: the synthetic estate produces it for the ownership tree and the dependency graph with the same incident; the engine produces it for its derived graphs.
- Limits: dense batches only reach elements that still sit in their snapshot slot; the synthetic generator does not produce telemetry for pods added by patches. Scrubbing before the stored window shows the oldest stored frame.

## Engine source (protocol version 3)

`EngineSource` (`src/source/engine.ts`, wire details in `engine-protocol.ts`) implements `GraphSource` over `engine/PROTOCOL.md` version 3; the editor side is `src/editor/service.ts`.

- History over HTTP from immutable URLs, then one WebSocket subscription `{op: "subscribe", graphs, after: seq}` for all graphs. Every record is validated against the contract schemas; invalid records and protocol errors appear in the Rejected list.
- Reconnect with backoff (0.5, 1, 2, 5 s), resume after the last sequence number, a skipped revision filled over HTTP, `gap` and `AheadOfHead` trigger a resync (reload from a snapshot), `SlowConsumer` reconnects, `activation` resets stored telemetry and reads it again.
- Lineage: selecting a derived element reads `/graphs/{g}/lineage?element=` and highlights its sources in the other graphs.
- The `catalog` graph is served like any other, with the kernel as its ontology; the editor reads it through `src/core/catalog.ts` (modules, types, identity domains, projections, operators, ports, wires, rules with direction class).

## Engine protocol notes

`engine/PROTOCOL.md` version 3 with the 3.1 corrections, against the engine built from the working tree on 2026-11-10. The workarounds for the version 3 mismatches are gone: the stream resumes after `seq` of `GET /space`, restore uses the patch in its answer, skeletons come from `POST /drafts/{id}/skeleton` and carry placeholders for required slots, a module version bump commits and rewrites its dependents' import pins (the text-to-graph diff includes the modules `/check` reports as affected), `catalog/meters` is no longer asked for.

Found while verifying (not worked around silently):

- Extract of a lens rule (`tree` of `capabilityView`) answers a patch; the draft then has two problems (`source of Under is emitted by no create emit of this projection`, same for the target) because the new projection emits the relationship but not its endpoint entities. Extracting `capabilities` and `tree` together answers `UpdateWithoutCreate` (`counts` updates what moves). Inline and move rule apply cleanly; undo of all three restores the module.
- An identity component built without its `component` relationship made the module unprintable with `Value cannot be null. (Parameter 'key')`, a raw exception with no element id (the canvas now builds the relationship).
- A patch that removes and creates the same element id answered HTTP 500 with an empty body (the canvas now coalesces such edits into one change).
- Constraint kinds, equivalence policies, row types and rule slots are not described by `/palette`; the canvas builds them from fixed shapes (`src/editor/structures.ts`). Constraint kinds other than acyclic, cardinality, enum and pattern are not offered. `/palette` also lacks what a Link policy is; the canvas keys it on the `left` and `right` identity slots.
- Unchanged: the kernel ontology uses `valueKind: "any"` (reported in Rejected, loaded as sent), revisions carry no commit time (placed by order on telemetry windows). Dangling relationships (`dangling` per graph in `/space`) are drawn to reference stubs (see Views); only those beyond the stub cap are counted in the status bar as not drawn.
- A Match with no pattern node and similar incomplete operators now answer `Unprintable` with an element id; the id is the projection (`Projection deploymentHealth is incomplete: a required slot, reference or value is missing`), not the Match, so the canvas cannot flag the card.
- A constraint whose name is not the engine's default (`kind-Type[.property]`) prints as a named constraint and breaks the module text; the canvas names constraints by that default (a key has no property in its name).
- The graph space's `activation` that names a new graph makes the canvas reload the source (see below).
- Not used: `POST /graphs/{g}/edits` and the editability endpoint.
- Stacked projections: the seven projections of `acme.healthmodel` open without problems, with a breadcrumb from the source graph to the health graph.

## Visual language

- Role colors follow `brainstorm/tools/story.py`: input amber, master teal, projection blue, rule purple, identity pink, document lime, diff coral. Chrome colors are Fluent tokens.
- Color is never the only signal: node shape and label give the type; added is a solid ring and `+`, changed a double ring and `Δ`, removed a dashed ghost and `−`, same entity elsewhere a pink ring, source element a dashed ring; editor problems are `✖` and `⚠` with text.
- Direction class (`forward ⇢`, `readonly ⇥`, `bijective ⇄`, `lens ⇋`, `sync ↻`, `mixed ⇅`) is a first-class attribute: glyph and word on the projection, on rule cards and in the graph headers.
- The WebGL view has light and dark palettes; high contrast uses the dark palette.
- Layout is responsive: below 1000 px the panels stack.


A source describes a graph space and yields, per graph, a snapshot and then ordered patches.

- `telemetry` (optional) is the telemetry feed described above.
- `open()` returns the space: for every graph its id, role (master or projection), `GraphDescriptor`, `OntologyDefinition`, the producing `ProjectionDefinition`, and the graphs that feed it (`inputs`, `inputPorts`).
- `snapshot(graph)` returns the initial state (flat model: entities, relationships, version).
- `subscribe(graph, sink)` delivers `{type:"patch"}`, `{type:"rejected"}` and `{type:"end"}` events in order and returns an unsubscribe function. A live source keeps calling the sink.
- `correspondences(graph)` (optional) returns derived element to source elements records.
- `evaluate(definition)` returns `unavailable` or an output snapshot.
- `onRejected(cb)` reports every record that failed validation. The UI shows a counter and a list; nothing is dropped silently. Patches that do not apply (wrong revision, stale before-state) are reported the same way.
- `controls` (optional) gives play, pause, step, reset and speed for replaying sources. `review(graph)` (optional) gives two versions of a definition and their outputs.
- Wire shapes are the ones in `brainstorm/contracts/schemas/`: `GraphPatch`, `GraphDescriptor`, `OntologyDefinition`, `ProjectionDefinition`, `GraphSpaceDefinition`, plus `EntityState` and `RelationshipState` inside snapshots. Validation uses those schema files directly (`src/core/validate.ts`).
- An engine WebSocket or NDJSON source implements the same interface: `open` and `snapshot` from the first messages (a `GraphExtent` page plus descriptor, as in `SnapshotPage` and `SnapshotSeal`), `subscribe` forwards `GraphPatch` messages after validating them.

Implementations:

- `StaticSource` (`static.ts`): a manifest JSON points at a `GraphSpaceDefinition` file and, per graph, an ontology, a snapshot file `{descriptor, extent}`, optional patches (JSON array, single patch, or `.ndjson`) and optional correspondences `[{target, sources:[{graph,key}]}]` with keys `n:<entity id>` or `e:<relationship id>`. Examples: `public/demo/operations/space.json` and `public/demo/repo/space.json`.
- `SimulatedStream` (`simulated.ts`): wraps any source and delivers its patches under play, pause, step, reset and a patches-per-second control; each tick delivers the next patch of every graph.
- `SyntheticSource` (`synthetic.ts`): the estate generator with an ownership tree and a workload dependency graph derived from the master, their definitions, ontologies and correspondences. Generated data is trusted and not schema validated per record.
