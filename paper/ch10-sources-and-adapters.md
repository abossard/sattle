## 10.1 Definitions

**Definition 10.1 (adapter).** An adapter is compiled engine code that reads the native records of one source and produces **rows** of a declared row contract (a `RowType` of an adapter module, Def. 2.2) together with coverage controls. It hides vendor formats and versions. It does no identity resolution and creates no graph facts. Each adapter declares the digest of the row-contract release it produces and is registered under an id (`Source.adapter`, Def. 5.8). Adding an adapter is an engine release (Ch. 2, gap 1).

**Definition 10.2 (envelope, delivery key).** A captured or transported record is an envelope `{v, source, capturedAt, seq, key, meta, payload}`. `payload` is the native record untouched, `meta` is capture-side context (query, page, resume token), `capturedAt` is the receipt wall clock and *not* event time (event time is inside the payload and becomes observed time `τ`, Def. 7.2), and `seq` orders the records of one file only. The **delivery key** `key = <source>/<natural id>` is stable: the same record delivered twice has the same key. Where no natural id exists, the key is a hash of payload and a salt (`lab/CAPTURE-FORMAT.md`).

**Definition 10.3 (observation, contribution, withdrawal).** An observation is an adapter row with its source, delivery key and position. A *contribution* is the set of fragments (Def. 9.7) that one source record causes, identified by a stable **contribution key**. A contribution can be replaced or withdrawn by its source without deleting other support for the same resulting graph fact (`ADAPTERS.md`).

**Definition 10.4 (coverage, authoritative absence).** A coverage control is a declaration `Coverage(scope, level, scan)` by an adapter: the scan `scan` claims to have enumerated every record of `scope` at consistency `level`. **Authoritative absence** of an element in scope is the closed-world conclusion drawn from a coverage declaration. Without one, absence from a result is unknown, not deletion. A reconciliation policy is a rule `reconcile(source, scope)` that withdraws the contribution of every element of `scope` not returned by a scan whose declared consistency level is at least the level `ℓ` that the policy requires.

**Definition 10.5 (ingestion pipeline).** One pipeline, in this order (finding 9): the adapter turns native records into rows. The **ingestion projection** (purpose `ingestion`, Def. 5.1) resolves identity (`IdOf` over row fields, Def. 5.9, `alloc` or lookup, Def. 1.9, 1.10) and emits the facts of the master graph. The contract's `EntityCandidate` with an `IdentityKey` inside the adapter and the separate adapter-side mapping `ProjectionDefinition` are replaced by this split. The ingestion projection is mandatory, not optional.

**Definition 10.6 (structure and telemetry rows).** A row contract field is graph data or telemetry by the ontology property it feeds. Observations about topology and state (resources, objects, events) feed the structural plane. Counters, flow aggregates and metrics feed the telemetry plane as samples `(τ, w, x, i)` (Def. 7.2). Rule A1 (Ch. 11): a flow is a sample on a relationship, never a relationship.

Per-source rules (`ADAPTERS.md`, restated with the definitions above):
- **Hubble.** Endpoint identity is scoped by cluster and namespace when only names are available. IP reuse is not timeless identity evidence. A `lost_events` record is explicit incompleteness (`Partial(sourceLoss)` on the affected windows, Def. 7.7) and never an inferred deletion.
- **Azure Resource Graph.** A resource returned by a query is an observation. Completion of pagination is not strong point-in-time consistency. Deletion by absence needs a declared reconciliation policy, because query filters, partial scopes and eventual indexing prohibit an unconditional rule.
- **Kubernetes.** Event warnings are observations about objects, not state changes. The Kubernetes `resourceVersion` is source data and an equality and resume token for the watch. The engine does not rely on its order: the current API documentation guarantees orderable integers for kube-apiserver types from Kubernetes 1.35 ([k8s-api-concepts]), and the lab cluster runs 1.34 (`lab/CAPTURE-FORMAT.md`). A UID plus cluster scope identifies a pod, and a deployment aggregation uses a different identity domain (Ch. 5). `DELETED` withdraws the source's contribution while another source may still support the entity. Expired watch history requires a relist.
- **Network Watcher.** Parse the tuple layout by `flowLogVersion`, never with one positional parser. Prefer VNet flow logs. Legacy NSG logs are an explicit binding and retire on 30 September 2027 (Fact 0.4).
- **OpenTelemetry.** A resource gives identity context, not a cross-source identity (Fact 0.5). `service.instance.id` is modelled separately from `service.name` grouping. Metrics are interpreted by temporality: delta sums and cumulative counters map to the `(temporality, combine)` of the target property (Def. 2.11).

## 10.3 Theorems

**Theorem 10.1 (idempotent delivery).** Re-delivering a record with the same delivery key does not change the graph or the support of any element. A distinct repeated observation (a new key) is a new contribution.
Status: **proved**.

*Proof.* Contributions are keyed: replacing the contribution of key `c` by the same fragments leaves the support function `σ` of Def. 9.7 unchanged, because `σ` is the sum over keyed contributions, one term per key. A transport batch is not a transaction and carries no semantics (ARCHITECTURE.md). Telemetry samples are de-duplicated on `(k, p, τ, i)` (Def. 7.2). ∎

**Theorem 10.2 (withdrawal removes one source's support).** A withdrawal by source `s` removes exactly the contribution of `s` for the withdrawn record. The element remains iff its support from the other contributions is positive.
Status: **proved** (Def. 9.7, Theorem 9.5).

**Theorem 10.3 (soundness of reconciliation).** If a scan `scan` satisfies its coverage declaration `Coverage(scope, level, scan)` (it did enumerate every record of `scope` at that level), then the withdrawals of `reconcile` are exactly the records of scope that have been deleted at the source at the scan's consistency level. No reconcile rule may fire without a coverage declaration with `level ≥ ℓ`.
Status: **proved relative to the declaration.** Whether a particular source's scan meets its declaration is an external fact and an **obligation** per adapter (O10.1), checked against the lab capture: ARG pages report `$skipToken` and `resultTruncated`, Kubernetes list gives a consistent snapshot at one resource version.

*Proof.* By Def. 10.4 an element of `scope` absent from a complete scan is absent from the source at that level. Withdrawing its contribution is the definition of deletion for a source that has no explicit delete record. Elements outside `scope`, and elements of a scan without declaration, are not touched. ∎

**Theorem 10.4 (loss is not deletion).** No `lost_events`, truncated page, throttled query, expired watch or failed read causes a withdrawal. It marks coverage as incomplete (a `Partial` closed window for telemetry, an `Unavailable` or `MoreAvailable` outcome for reads, Def. 11.7) or triggers a relist.
Status: **proved** by construction: withdrawal is produced only by explicit delete records (Theorem 10.2) and by reconcile rules (Theorem 10.3), and neither fires on loss.

**Theorem 10.5 (list then watch, resumption).** Assume the premises KW1 to KW3 on the Kubernetes API. Let a list of a collection return the object set `O₀` and the `resourceVersion` `v₀`, and let a watch started at `v₀` have delivered the events `ε₁ … ε_n` without a 410 response. Let `O_j` be `O_{j−1}` with `ε_j` applied: `ADDED` and `MODIFIED` put the object under its uid, `DELETED` removes it, `BOOKMARK` changes nothing. Then `O_n` is the state of the collection after the operation that `ε_n` reports. If the watch ends with 410 Gone, a new list gives the state at its own `resourceVersion`, and the statement applies again from there.

**Premises (the list-and-watch contract, [k8s-api-concepts], section "Efficient detection of changes", read on 2026-11-11).**
- **KW1.** A list returns the objects of the collection as of one `resourceVersion`, and returns that version.
- **KW2.** A watch started at a `resourceVersion` delivers one event for every create, update and delete on the collection after that version, with the outcome of the operation, in the order of the operations. The documentation says that the stream itemizes the outcome of the operations after the given version and that the mechanism lets a client follow changes "without missing any events"; that the events arrive in the order of the operations is this paper's reading of "stream of changes", and the theorem needs it.
- **KW3.** A server keeps the history of changes for a limited time. A watch that asks for a version older than that fails with 410 Gone, and the client must list again and watch from the version the list returns.

Status: **proved under the named premises KW1 to KW3**, restated. The premises are properties of an external system, taken from its documentation; this repository cannot test them, and the theorem is as strong as that documentation. The lab capture follows the protocol (`lab/CAPTURE-FORMAT.md`). The first form asserted the conclusion with a citation and no premise.

*Proof.* By induction on `n`. `O₀` is the state at `v₀` (KW1). Let `O_{j−1}` be the state after the operation of `ε_{j−1}`, or at `v₀` for `j = 1`. By KW2 the next operation on the collection is the one that `ε_j` reports, and the event carries its outcome: after a create or an update the object is as the event gives it, after a delete it is gone. Applying `ε_j` to `O_{j−1}` therefore gives the state after that operation. A `BOOKMARK` reports no operation. After a 410, KW3 and KW1 give a new base. ∎

*In the engine.* An `ADDED` or `MODIFIED` event replaces the contribution of the object under its delivery key and a `DELETED` event withdraws it (Theorems 10.1 and 10.2). A relist is a coverage declaration for its kind (Theorem 10.3): what the engine knows of the kind and the list does not mention is withdrawn (10.6, forwarder markers).

**Theorem 10.6 (replay of a capture is deterministic).** Define the input order of a capture as the order sorted by `(capturedAt, file path, seq)`, and give each record the ingestion sequence of its position. Then, with pinned definitions, replaying the capture into the engine produces the same revision log on every run.
Status: **proved**, given T7 (Theorem 6.3).

*Proof.* The sort key is a total order on the records of a capture (files of several processes carry separate sequences, so `capturedAt` and the file path break ties between files, and `seq` orders within a file). The resulting sequence is a recorded input sequence, and Theorem 6.3 applies. ∎

The order of a capture is an *arrival* order of the capture tooling. It is not the order in which the sources emitted events. The engine does not promise identical results for different interleavings of independent sources (ARCHITECTURE.md). B1 replays captures at 1, 10 and 100 times speed (Ch. 13) by compressing the `capturedAt` differences, not by reordering.

## 10.4 Identity of observed endpoints

- A flow names its endpoints by namespace and pod name, plus Cilium identities. Name-based keys can move: `podName(cluster, namespace, name)` rebinds when a pod of a StatefulSet is recreated under a new UID ([R03] section 5, open question Q5). Under the ingestion order, a flow is attributed to the pod that held the name at that position of the log.
- Endpoints identified by IP address only are **observation-scoped**: they are keyed by cluster, address and a time-bounded lease, or labelled as observation-scoped, because IP reuse is not timeless identity (finding 29, `ADAPTERS.md`).
- Rows from several adapters resolve to one entity iff they use the same identity domain and equal canonical components (Theorem 1.4) or through an accepted equivalence (`Link`, Ch. 5). The Kubernetes `Pod` row uses `podUid` and links `podUid` and `podName` with confidence 1.0 ([R03] section 8.2). Experiment **Q5** compares the two attributions on a recorded StatefulSet restart.

## 10.6 VNet flow logs and the live stream

**VNet flow logs as a source.** The tuples of one record are rows of the row contract `FlowLogRow` (one row per tuple, `engine/definitions/sattle.source.azure.sattle`). One readonly rule of the ingestion projection, `observedFlowLogs` in `acme.ops`, keeps the tuples with state `D` (denied) or `B` (begin), windows them by tuple time in 60 s windows with the late policy `revise`, and updates the virtual network resource with the telemetry properties `deniedFlows` and `newFlows`. The health signal "denied flows" of 7.5 reads the first. The rule creates no endpoint entities: the source and destination addresses and the states `C` and `E` are rows that no rule uses, and tuples are not joined into connections. The tuple timestamp is event time (observed time `τ`, Def. 7.2); the record time is the platform write time. Observed time is therefore not monotone: tuples inside a record are not sorted and a later record can carry older tuples, so rows arrive late for their windows. A re-read of a blob returns the same records, so delivery is idempotent only through the delivery key (Theorem 10.1), and the capture format deduplicates on blob path plus record time.
Measured on the first real capture (`lab/CAPTURE-FORMAT.md`, `paper/evidence/replay-head-105738.txt`): 522 records with 175,265 tuples, of which 85,491 `B`, 85,476 `E`, 4,170 `C` and 128 `D`, from 10:19:47Z to 12:30:48Z, and 175,265 rows consumed with 0 rejected (the states were counted by this paper from the capture file). The lab policy that blocks reading the blobs from a laptop is worked around by a short-lived reader pod in the cluster (`lab/README.md`). Endpoint identity for flow logs (observation-scoped by address, 10.4) is therefore **not exercised**.

**Event Hubs records and evidence elements.** Two adapters read the diagnostic-settings hubs of a capture (`eventhub/sattle-activity.ndjson` and `eventhub/sattle-aks.ndjson`, the same rows a live input would give): `azure.diagnostic-activity` turns Activity Log records into `ActivityRow`, `azure.aks-audit` turns `kube-audit-admin` records of completed requests into `AuditRow`. Evidence is one element per operation and not only a count: an `ActivityEvent` with a `Concerns` edge to its Azure resource (the resource id is grouped case-insensitively, which is what fixed the first cause of D17), a `WarningEvent` with an `About` edge to its pod for Kubernetes events of type `Warning`, an `AuditEvent` (lease renewals are left out by the rule) and, in the health graph, an `Evidence` element with an `EvidenceFor` edge to its component (Ch. 7, 7.5). The counts stay as telemetry. Tests: `EvidenceAdapterTests.cs` (a started and a succeeded record give two events with one `Concerns` target whatever the case of the id; only completed audit requests and no lease renewals; only the warning of two events is an element). **Definition 10.7 (live input).** A live input is a reader of an Event Hub whose events are capture envelopes (Def. 10.2). It uses the same adapters as replay. Its logical time advances from the recorded `capturedAt` of the events, never from the wall clock, so it is an input of the same kind as an `Advance(λ)` control of a replay. The reader checkpoints by delivery key and sequence number, drops duplicates by key, and records every consumed envelope to a stream file. A replay of that file is meant to reproduce the state digest of the run.

**Proposition 10.7 (live run reproduced by replay).** Let a live run consume the envelopes `e_1 … e_N`. Under the premises LV1 to LV4, a replay of its stream file with the same definitions ends in the state digest of the live run.
- **LV1 (the recording is the consumed sequence).** The stream file holds exactly `e_1 … e_N`, each once, in consumption order.
- **LV2 (an envelope gives the same inputs in both runs).** The rows and the logical-time advances that an envelope causes are a function of the envelope, the envelopes before it and the options of the run (`--advance-every`, `--lateness`): an adapter is a function of the record (Def. 10.1), and logical time advances from the recorded `capturedAt` (Def. 10.7), never from the wall clock.
- **LV3 (same horizon).** The replay uses the late horizon of the live run.
- **LV4.** The premises B1 to B4 of Theorem 6.2 hold for the definitions and the input.

Status: **proved under the named premises LV1 to LV4**, restated. Read only. LV1 and LV2 are properties of the reader loop `LiveInput.Run` and of the adapters, LV3 a property of how the replay is invoked. They are **tested by examples against a stand-in or a fake source, never on Event Hubs**, and the reproduction test drives a loop of its own with the same steps, not the reader of `Live.cs`. Wanted: test T-LIVE on the real loop ([inventory.md](inventory.md)); a run on Event Hubs needs a cluster. The first form listed three premises without names and gave a sketch.

*Proof.* By LV1 and LV2 the live run and the replay evaluate the same sequence of inputs: the same rows and logical-time controls, in the same order, with the same ingestion sequence numbers. They differ only in where the sequence is cut into steps: the live run flushes its pending chunk at points that depend on timing, and the replay cuts by chunk size. By LV3 the test whether a row is late is in both runs the same function of the row and of the frontier at its position (premise B2). By Theorem 6.2(b), which needs LV4, the state after the last input is the same for every cut. The state digest is a function of the state (Theorem 3.3). ∎

The two commit logs can differ, because a step loses the revision boundaries inside it (Theorem 6.2(b)); the proposition is about the state digest.
- *Reproduction.* `LiveReproducibilityTests.cs` writes the envelopes of the fixtures in a shuffled arrival order (every line moved up to 0, 6 or 40 places from its capture-time position, seeds 1 to 3), processes them one by one with the late horizon of a live run (3) and flushes the pending chunk at random points, then replays the recorded stream in file order with `--no-flush` and the same horizon. The state digests are equal in the three cases. A second test checks that the recording is read in file order and not in capture-time order. A third, in the capture category, does the same on the newest real capture (distance 25, seed 5). These tests use a loop of their own with the same steps, not the reader of `Live.cs`.
- *Order and kills.* In `LiveInput.Run`, the loop that every live source goes through, the order for an envelope is receive, journal (with the source position), record, process. The journal is the truth and is written first, the recording never holds an envelope the journal lacks, and a start that finds the recording shorter than the journal appends the missing envelopes before it reads the source. `LiveCrashTests.cs` kills a run at each of the four steps of the envelope with index 2, 25 and 60 of 80 shuffled envelopes of the `estate` fixture (an exception raised from a hook of the host, on the in-memory store) and starts again: the digest equals the uninterrupted run's, the recording holds every envelope once and in order, and a second restart changes nothing. Another test removes the last five lines of a recording and finds them restored from the journal.
- *The command.* The live input and `serve --live` keep three window widths, and `replay` keeps a million by default, so a live run is reproduced by `sattle replay <live-out> --no-flush --late-horizon 3 --cluster NAME` (plus the `--advance-every` and `--lateness` of the live run). Without `--late-horizon` a row that the live run dropped as late would be kept by the replay; whether the digests then differ was not tested.
- *Not done.* A run on Event Hubs. It needs Azure, and no cluster exists (10.5).

**Definition 10.8 (live resume).** With a durable store, the live input journals the envelope together with the position of its source (for Event Hubs the partition and the sequence number, after the envelope) before it processes it, journals a record that is a duplicate or not an envelope as a position alone, and journals each flush of the pending chunk, so that a restart cuts the chunks where the live run cut them. A restarted run reads the last position back and the source continues after it. An envelope delivered again is dropped by its delivery key; the last 20,000 keys survive a restart. Without a store there is no resume.

**Proposition 10.8 (a killed live run resumes to the state of an uninterrupted run).** Let a source deliver envelopes `e_1 … e_N` in a fixed order. Under the premises LR1 to LR4, a run that is killed after it has journaled `e_k`, and restarted from its store, consumes exactly `e_{k+1} … e_N`, each once, ends in the state digest and the input row count of the uninterrupted run, and a second restart gives the same state again.
- **LR1 (journal first, whole entries).** The live input writes an envelope to the journal, with the position of its source, before it processes it, and journals every flush of the pending chunk; after a kill a journal entry is wholly present or absent. This is premise J1 of Proposition 11.9 for the live path.
- **LR2 (the source resumes).** After a restart the source continues after the journaled position of `e_k`, or delivers again a suffix of the envelopes whose delivery keys are among the last 20,000 journaled.
- **LR3.** The premises J2 and J3 of Proposition 11.9.
- **LR4.** The premises B1 to B4 of Theorem 6.2.

Status: **proved under the named premises LR1 to LR4**, restated. Read only. LR1 is read from `SpaceHost.LiveEnvelope` and tested with a simulated kill, an exception raised from a hook, not a process kill, and not during the write of one journal entry; LR2 is a property of the source, tested against a fake source that is a list of envelope lines with positions; the Event Hubs source is code that no test or run reads from. Wanted: test T-RESTART on the live path ([inventory.md](inventory.md)).

*Proof.* By LR1 the journal at the kill holds `e_1 … e_k` with their positions and the flushes between them, and of `e_{k+1}` nothing (if it holds `e_{k+1}` whole, rename `k`). By Proposition 11.9, whose premises are LR1 and LR3, the restart reproduces the state after the journal: the state of the killed run after `e_k`, with its chunk cuts, the last source position and the last 20,000 delivery keys, which are functions of the journal. By LR2 the source then delivers `e_{k+1} … e_N`, possibly after envelopes that are already journaled; those are dropped by their delivery key (Theorem 10.1). So the resumed run has consumed `e_1 … e_N` in order, each once, cut into steps as the killed run cut them up to `e_k` and in some way after it. By Theorem 6.2(b) and LR4 the state after `e_N` does not depend on the cut, so it is the state of the uninterrupted run; the row count is a function of the consumed envelopes (premise LV2 of Proposition 10.7). A second restart is Proposition 11.9 again. ∎

**Tested by examples against a fake source** (`LiveResumeTests.cs`): the envelopes of the synthetic `estate` fixture arrive in a shuffled order (seed 4, up to 12 places), the run is killed after 60 percent of them plus 7, between two idle points so that the rows of several envelopes are pending in the chunk, and is restarted from the store on memory and SQLite (and on Cosmos when an emulator is given, which this paper did not use), with a seal every 30 entries and with none; the digest and the row count equal the uninterrupted run's, exactly the remaining events are consumed with no duplicate, and a second restart gives the same digest and the position of the last event. A source that delivers the last 9 events again has them dropped as 9 duplicates. A record that is not an envelope is rejected, counted, and its position kept. The kills are also tested at each step of an envelope (`LiveCrashTests.cs`, Proposition 10.7). **Not tested:** a real Event Hub, more than one partition (the source reads one and warns), a source that redelivers more than 20,000 envelopes, a process kill and a kill during the write of one journal entry. **Measured transport capacity of the lab forwarder** (`lab/CAPTURE-FORMAT.md`, "Capacity", one Event Hubs namespace of Standard tier with one throughput unit, one partition on the ingest hub, one sequential sender per hub; figures are lab measurements recorded in that file, single runs, not re-run by this paper):

| Run | Rate | Duration | Result |
|---|---|---|---|
| flows, not mirrored | 86 flows/s | 14 min, with a relay restart | clean, RSS at most 101 MB, queue near 0 |
| flows, mirrored to a second hub | 62 flows/s | 8 min | clean |
| flows, mirrored | 107 flows/s | 1 h | saturated, 36,000 events dropped, about 9 % duplicated by retries |
| flows, mirrored | 286 flows/s | 5 min | saturated, 16,000 dropped events reported, RSS 244 MB, queue held at 64 MB |

A flow envelope is about 4.4 KB. In saturation the delivered rate stays near 125 events/s, about 0.55 MB/s, below the nominal 1 MB/s of one throughput unit. The lab plan is therefore 125 events/s in total across hubs, about 125 flows/s unmirrored or 60 flows/s mirrored. Beyond it the forwarder queues up to 64 MB per hub and then drops the oldest events with a `dropped` marker, whose count is a lower bound while the hub is overloaded.
- *Bearing on the hypotheses.* The engine, on a replay of the real capture, processed about 67,000 records per second in memory (`engine/PERF.md`, Ch. 13, H1). The transport of one throughput unit with a single partition, one in-flight send for ordering, is about 40 times below the H1 target of 5,000 records per second per graph space. For the lab, the transport and not the engine limits live ingestion. The capture rate of the Hubble flows themselves is about 325 flows per second (235,858 flows in 725 s), above the measured delivery of 125 events per second, which is why the forwarder filters at the source (namespaces `sattle-demo` and `demo` by default). H5 (source to graph latency) is **not measured** for the live path.
- *Loss is not deletion.* The forwarder reports its own loss and restarts as markers (`start`, `stop`, `relist-start`, `relist-end`, `dropped`, `hubble-reconnect`, `watch-expired`, `watch-error`, `poll-failed`). They are the coverage declarations of Def. 10.4 for the live path. The engine consumes five of them (`PROTOCOL.md` 3.3, `ForwarderMarkerTests.cs`). A `relist-start` to `relist-end` pair is the complete set of one Kubernetes kind (pods, services, nodes, deployments, endpoint slices): what the engine knows of that kind and the list did not mention is deleted. A relist that never ends (a crash) deletes nothing. `dropped`, `hubble-reconnect` and `poll-failed` mark the telemetry window that contains them `Partial(forwarderDropped | hubbleReconnect | pollFailed)` with the dropped count, several kinds in one window joined with `+`. This is Theorem 10.3 for the five kinds and Theorem 10.4 for the telemetry windows. The tests are fixture tests: a relist replaces the known set (parametrized over four of the five kinds, endpoint slices untested), a relist without end and a relist of another kind leave a kind alone, the three loss markers mark their window, two kinds in one window are both named. No capture exercises them: the forwarder's records sit in `eventhub/sattle-ingest.ndjson`, which replay does not read, and the live input is not run by this paper.
- *Markers not consumed.* `start`, `stop`, `watch-expired` and `watch-error` have no effect in the engine (the README lists the five consumed). `watch-expired` is followed by a relist, which repairs the loss. A `dropped` marker means state is stale until the next relist (`lab/CAPTURE-FORMAT.md`); the engine marks the window and does not mark the graph stale. A crash without `stop` is not treated as stale state either, except that its unfinished relist deletes nothing.

**Definition 10.9 (source progress, heartbeat).** Agreed with the engine core session on 2026-11-12, not built. Every envelope that a source delivers records the *progress* of that source: the pair of the source and the capture time of the envelope, as an input with a recorded position like any other. An envelope that carries no row counts as well: a forwarder marker, or a *heartbeat*, an envelope a source sends only to say that it is alive and has nothing to report. `coveredUntil` of Def. 7.14 is computed from these records, so coverage is a recorded fact and a replay sees the coverage of the live run.
- A source that reports only when something happens (Kubernetes events, the Activity Log) is silent when nothing happens and cannot be told from a source that is down. It needs heartbeats from the forwarder to be covered. The forwarder of the lab sends none, and the two real captures hold none, so on them such a source is covered only up to its last record.
- Progress is not a watermark in the sense of a promise that nothing older will come: late rows are still judged by the late horizon (Ch. 7, Def. 7.6). It says how far the source has reported.
