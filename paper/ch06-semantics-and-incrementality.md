# Ch. 6 Semantics and incrementality

**Claim.** The meaning of a projection is a function of its recorded inputs. Incremental evaluation computes that function, the result does not depend on how the input is cut into batches (under the premises B1 to B4), and a replay reproduces the revision log.
**Status.** Built: a vectorized interpreter over interned columns with an incremental strategy per operator, support-counted element layers, ordered evaluation with one atomic commit per graph, `Join` as a hash join with a bilinear delta, `Traverse` as bounded reach, `Fixpoint` as a bounded unrolling and not semi-naive iteration (D11). Tested: T6 and T7 on fixtures and on both real captures, where the state digest is one value at chunk sizes 1, 50, 777, 100,000 and the default (Ch. 14, 14.5); B1 and B2 by unit tests that fail when their fix is reverted; B3 on examples, with no generator of arrival orders; T9 and T10 on an acyclic example only. Proved relative to two cited theorems: T5, with cases corrected at gate 1a (`Match`, operators filtered by the frontier, `Threshold` as a fold of the recorded sequence, materialization). T6 has a fourth premise B4, found by deriving its proof again. Not built: `Delta`. Deviations D7, D9, D11, D14, D17 (resolved), D21 (resolved), D33, D34.
**Gate.** 1a (theory): incremental evaluation equals batch evaluation, batch invariance, determinism. The same results are the argument that gate 1c (efficient) builds on: work proportional to the change.
Uses: Ch. 1 (identity allocation), Ch. 3 (graph, log, frontier, clocks), Ch. 4 (patches, signed deltas, group), Ch. 5 (operators, typing, closed language), Ch. 7 (closed windows).
Used by: Ch. 7, 8, 9, 11, 13.
Sources: [R01] T5 to T10, findings 16, 21; [R02] L4; [R03] sections 3.3, 10, 11; ADR-004, 009, 017, 018, 048; [budiu2023] and [mcsherry2013] for incrementalization.

## 6.1 Inputs and the semantic domain

**Definition 6.1 (input log).** The input log of a graph `g` with projection `P` is the sequence `ι = (i₁, i₂, …)` of inputs that `P` consumes, in the engine's recorded ingestion order (ADR-017, ADR-018). An input is one of: a batch of rows for a rows port; a graph change (a committed patch `E_r` of an input graph, with its frontier) or a snapshot of an input graph; a logical-time control `λ`; a closed-window record (Def. 7.7) of an input graph or of the projection's own ingestion windows. Each input carries its ingestion sequence number `s`. Configuration edits are handled in Ch. 9. Time passing alone changes nothing (ADR-048): only a `λ` input advances logical time.

**Definition 6.2 (Z-set streams).** For each port, rows are finite-support maps `ℤ^(Row)`, the group of Def. 4.6 over rows. A stream is a sequence of such maps indexed by input position. The *integral* `I` sums a stream prefix, the *difference* `D` takes successive differences, so `D ∘ I = I ∘ D = id` on streams that start at `0`. The state of a graph input port after `n` inputs is the integral of the facts of the patches received. It is a materializable Z-set, the embedding `χ(G)` of a graph (Def. 4.7).

**Definition 6.3 (denotation of an operator).** Each operator kind has a function from the Z-sets of its in-ports to the Z-set of its out-port (the *batch semantics*):
- `Match`: the Z-set of variable bindings of the pattern over the facts of the graph port. A node pattern is a selection on entity facts, an edge pattern a join of a relationship fact with its endpoint entity facts (an endpoint that is absent from `G` does not bind, so dangling relationships bind only patterns that do not require the endpoint entity).
- `Filter`, `Map`, `Union`: pointwise on rows, `Union` per its conflict policy (Def. 5.10), `Map` by evaluating expressions of the closed function set.
- `Join`: the equijoin with weights multiplied. `Distinct`: weight `1` where the weight is positive.
- `Group`, `Rollup`: per key, aggregates over the rows with weights as multiplicities. `Traverse`: bounded reachability over relationship facts by **shortest distance**. For a start `s` the output has one row per element `t` whose distance `d(s, t)`, the length of a shortest path in the given direction, satisfies `minDepth ≤ d(s, t) ≤ maxDepth`, and the depth column is that distance. `d(s, s) = 0`, so a start is in its own result only with `minDepth = 0`, also when it lies on a cycle. It is not the union over path lengths: that reading gives several depths per pair, counts walks on cycles, and differs from this one for `minDepth ≥ 2` and on a cycle through the start.
- `Window`: assigns `windowStart` and `windowEnd` by the aligned grid (Def. 7.5). A window is *closed* by a `λ` input (Def. 7.6) and releases its rows then.
- `Fixpoint`: the least fixpoint of the body (Def. 6.9).
- `Series`, `Rollup` on windows, `Delta`, `Threshold`: Def. 6.7.
- Sinks: `EmitEntity`, `EmitRelationship`, `Link` produce *fragments* `(key, partial state)` with weights.

**Definition 6.4 (denotation of a projection, output graph).** `⟦P⟧` maps the integrated input state `S` (a family of Z-sets, one per port) to the output graph `O(S)` by composing the operator functions along the operator graph and then *materializing* the fragments. For each element key `k`, the support `σ(k) = Σ weights of fragments for k`. The element is present iff `σ(k) > 0` and some create fragment exists for it (update fragments for absent keys have no effect). Weights add in any order: a Z-set has no order (Def. 6.2), so a retraction may reach a sink before the insertion it cancels, inside one batch or across batches, and `σ(k)` may be negative in between. A sink is linear in the weights and keeps a negative support; it does not drop it. Its state merges the property assignments of its positive fragments, and the merge is a function of the multiset of fragments: no order of sinks, statements or arrival enters it, and an update fragment does not override a create fragment.
- *Property conflict.* If the positive fragments of a key assign more than one value to a property, the property is **absent** on the element, and the key, the property and the values are a *conflict*: reported with the commit and counted.
- *Type conflict.* If the positive create fragments of one key disagree on the type of the element, or on the endpoints of a relationship, the element is absent and the conflict is reported: an element has one type and one pair of endpoints, and no order of sinks picks one.
- *Uniqueness conflict.* If more than one relationship with positive support has the same `(source, target, type)`, the one with the smallest `rid` (Def. 5.9) is present, the others are absent and reported as conflicts, so the result satisfies `U`.
- *No failure of the event.* A conflict does not fail the projection event. Iteration 0.1 and the first form of this definition failed it atomically; that stops a whole graph on one bad key and was never what the engine did.
- *What batch invariance requires* (Theorem 6.2). Only that the outcome does not depend on arrival order or chunking, which any function of the fragment multiset gives. "The last arrival wins" violates it. "The last sink wins" would satisfy it and is rejected for another reason: the meaning of a module would depend on the order of its statements, which a refactoring does not preserve (Proposition 5.7).

**Definition 6.5 (incremental form).** For a function `Q` on Z-set streams, `Q^Δ = D ∘ Q ∘ I`. For a projection, the **engine step** consumes input `i_{n+1}` and produces the output delta `Q^Δ` of `⟦P⟧` for that input, which the engine turns into the edit set of the next commit (Def. 3.9), possibly empty.

## 6.2 Frontiers, cuts, telemetry progress

**Definition 6.6 (frontier order, consistent cut).** Frontiers are ordered as in Def. 3.10 (pointwise over source partitions and input graphs). A *cut* of a graph space assigns each graph `g` a revision `r_g`. A cut is **causally consistent** iff for every derived graph `g` and input graph `g'`, `φ_{g, r_g}.gin[g'] ≤ r_{g'}` (no graph reflects an input revision that the cut does not contain). A cut is **aligned** iff in addition all graphs reflect the same master revision. The frontier is evidence of dependencies and not a cut ([R01], ARCHITECTURE.md). Aligned frontier mode is open work (R13 of Ch. 11). Consistent snapshots in distributed systems are in [chandy1985]; the frontier terminology comes from timely dataflow ([murray2013]), where it has a partial-order meaning that the engine's frontier shares for source partitions.

**Definition 6.7 (telemetry operators as folds).** For one key and a sequence of closed-window records ordered by `windowStart`:
- `Delta`: `inc_j = x_j − x_{j-1}` if `x_j ≥ x_{j-1}`, else `x_j` (reset), `inc₁ = 0`.
- `Rollup` (additive functions): the aggregate of Def. 7.8 over the records grouped by key and window.
- `Series`: the closed windows in `[frontier − within, frontier)`. The look-back decides which windows a later operator reads as data and which keys have a row. It does not bound the history of a state.
- `Threshold`: the state machine of Def. 7.10 over the current *episode* of the key, started in `initial`; one row per key that has a window in the look-back, whose `status` changes on a state change. The state is not a function of the windows in the look-back alone: a key that entered `high` stays `high` while its values stay inside the band, also after the windows in which it entered have left the look-back.
Their batch semantics is the function of the *set* of closed windows per key, in `windowStart` order, together with the frontier. A revised window (late policy `revise`) is a retraction plus an insertion, and the incremental form recomputes the affected key from the revised window onward, over the retained windows and from the carried state of Def. 7.10.

**Definition 6.8 (telemetry progress in the frontier).** The entry `gin[g']` of a frontier is a pair `(r, tw)`: the consumed revision `r` of the structural plane of the input graph `g'` and the telemetry watermark `tw`, the ingestion sequence of the last closed-window record of `g'` consumed. `Series` over graph port `p` at an input reads exactly the closed-window records of `g'` with sequence up to `tw`. This is the telemetry frontier of Def. 7.11 for cross-graph reads. [R03] section 10 states reads in terms of "the projection's frontier" and does not say how the closed windows of another graph are pinned. Def. 6.8 closes that gap.

**Definition 6.9 (least fixpoint).** For a `Fixpoint` with body `f` over rows of type `R_rel`, `lfp(f, seed) = ⋃_{n ≥ 0} f^n(seed)` where `f^{n+1}(X) = X ∪ f(f^n(X))`, as sets (weights collapsed by `Distinct`).

## 6.3 Theorems

**Theorem 6.1 (incremental correctness, T5).** Let `Q` be the composition of the operator functions of Def. 6.3 of a projection. For the operators of the kernel, the incremental strategies of 6.4 compute `Q^Δ = D ∘ Q ∘ I`. In particular after every input `n`, the integral of the output deltas equals `⟦P⟧` applied to the integrated inputs, that is the batch result. For some operators the batch semantics has one more argument: `Retain`, `Series` and the release of a closed `Window` take the frontier, and `Threshold` takes the recorded sequence of its closed windows (Def. 7.10). The theorem holds with those arguments; for `Threshold` the batch result is therefore not a function of the integrated input alone.
Status: **proved** by structural induction on the plan, relative to two theorems of [budiu2023] that are stated in the proof and not re-proved (their statements were checked against the arXiv text 2203.16684 at gate 1a), for the operators the engine has. Read only, checked by no tool. A second reading at gate 1a added the cases `Match`, the operators filtered by the frontier and materialization, which the first proof did not list, removed a circular reference between the `Retain` case and Proposition 5.9, and replaced the `Threshold` case, which was wrong for the semantics of Def. 7.10. Two things are outside the proof. (1) An unbounded `Fixpoint` needs the nested construction of [budiu2023] Section 5 and [mcsherry2013]; the engine has only the bounded unrolling, which the proof covers. (2) That the code of each strategy of 6.4 is the rule proved here is a property of the implementation: obligation **O6.1**, tested through T6 on fixtures and both captures, and wanted as a generated test per operator (test T-INC, [inventory.md](inventory.md)).

*Proof.* Streams are sequences of Z-sets indexed by the input position. `I` is the running sum and `D` its inverse (`D(s)[n] = s[n] − s[n−1]`), so `I ∘ D = D ∘ I = id`. `z⁻¹` is the delay by one position.
- *Chain rule.* `(Q₂ ∘ Q₁)^Δ = D Q₂ Q₁ I = D Q₂ (I D) Q₁ I = (D Q₂ I)(D Q₁ I) = Q₂^Δ ∘ Q₁^Δ`. The same computation gives `(Q₁ + Q₂)^Δ = Q₁^Δ + Q₂^Δ` for a fan-in by addition. A plan is an acyclic composition of operators, so it is enough to show `o^Δ = D ∘ o ∘ I` for the strategy of every operator kind `o`.
- *Linear operators.* Cited: for an operator `Q` that is linear (`Q(a + b) = Q(a) + Q(b)`) and applied position by position, `Q^Δ = Q` ([budiu2023], Theorem 3.3). `Filter`, `Map`, `Union`, window assignment and the emits are of this kind. Their strategy applies the operator to the delta, which is `Q^Δ`. `Values` is a constant and not linear: its output stream is its rows at the first position and nothing after, which is `D` of the constant stream.
- *`Match`.* A node pattern is a selection on entity facts, which is linear. An edge pattern is a join of relationship facts with the facts of their endpoint entities, which is bilinear, followed by a map to the binding row (Def. 6.3). The chain rule and the two cited theorems apply.
- *Bilinear operators.* Cited: for an operator `×` that is linear in each argument and applied position by position, `(a × b)^Δ = a × b + z⁻¹(I(a)) × b + a × z⁻¹(I(b))`, where `a` and `b` are the delta streams ([budiu2023], Theorem 3.4). `Join` is bilinear. Its strategy keeps `I(a)` and `I(b)` as indexes and evaluates the three terms. `Traverse` with bound `maxDepth` is a composition of `maxDepth` joins and a union, followed by the minimum of the depth per pair of start and reached element and the test against `minDepth`; the joins are covered by the chain rule and the minimum is a per-key function (below).
- *Per-key functions of the integrated state.* `Distinct`, `Group` with any aggregate, and the fold `Rollup` (Def. 6.7) are not linear as operators on rows: a changed aggregate retracts one output row and inserts another. Each is a function `h` applied key by key to the integrated input of that key: `o(I(a))[n](κ) = h(I(a)[n] restricted to κ)`. The strategy keeps the integrated input per key (a multiset with weights or the fold state; for `count` and `sum` the running value, which determines the aggregate because these are additive), which is `I(a)` restricted to the key because integration is linear, re-evaluates `h` for the keys that the delta touches, and emits the difference between the new and the old value of `h` for those keys. For an untouched key the integrated input is unchanged, so `h` is unchanged and the difference is zero. The emitted stream is therefore `D(o(I(a)))`, which is `o^Δ` by definition.
- *Operators filtered by the frontier.* `Retain`, `Series` and the release of closed windows have a batch semantics of the form `o(S, λ) = S` restricted to `π(λ)`, where `π(λ)` is a set of rows that depends on the frontier: the live rows (Def. 5.15), the windows in `[λ − within, λ)`, the rows of the windows that `λ` has closed. The strategy keeps the integrated input, passes a row delta iff its row is in `π(λ)` at its position, and on an advance from `λ` to `λ'` emits `+S(r)` for the rows that enter `π` and `−S(r)` for the rows that leave it. By induction over the positions, `I(out)[n]` is `I(in)[n]` restricted to `π(λ_n)`, which is `o` on the integrated input: the induction is written out for `Retain` in Proposition 5.9, where rows only leave, and it does not use this theorem. Which rows count as input of a window is fixed by the late rule (premise B2 of Theorem 6.2).
- *`Threshold`.* The input of the operator is the windows of a key that are in the look-back, and a window that grows old is retracted from that input, while the state must not forget it (Def. 6.7). The state is therefore not a function of the integrated input of the operator, and the per-key case does not apply. The batch semantics is the fold `F` of Def. 7.10 over the recorded sequence of closed windows of the key: the windows of the current episode in `windowStart` order, each with its current value while it is in the retained range, and with the value it had on leaving the range after that. `F` is a fold from the left, so `F(w₁ … w_n) = fold(c_j, w_{j+1} … w_n)` with the carried state `c_j = F(w₁ … w_j)`. The strategy keeps `c_j` for the newest window behind the range and the windows after it. A value behind the range never changes, so `c_j` is never recomputed, and a revision inside the range folds again from `c_j`. The strategy thus holds `F` after every input and emits the change of the key's row, which is `D` of the batch result. A recomputation from the integrated input under the final structure would differ whenever the structure changed after a window left the range; that is not the batch semantics. `Delta` has the same shape and is not built.
- *Materialization.* The sinks are linear and produce fragments. The output graph is the function of Def. 6.4 of the integrated fragments, per element key (presence, type, merged properties) and per uniqueness tuple; the per-key case applies with those keys.
- *`Fixpoint`, as built.* The engine evaluates a `Fixpoint` with bound `max` as the `max`-fold unrolling of its body: a composition of `max` copies of the body operators with a union and a `Distinct`. It is a plan without a cycle, so the chain rule and the cases above apply.
- *`Lift`* has no strategy: it is replaced by other operators before planning (Ch. 5, 5.8). *`Link`* emits no row; its effect on identity is the subject of Proposition 1.8.
By induction on the plan, the incremental evaluation computes `Q^Δ`, and integrating both sides gives `I(Q^Δ(a)) = Q(I(a))`: the integral of the output deltas is the batch result on the integrated input. ∎

**Theorem 6.2 (batch invariance, T6, ADR-009).** (a) The output log of a projection does not depend on how the transport chunks the input sequence. (b) If the engine evaluates `g` consecutive inputs as one step, the output state after the step equals the state after the last of those inputs processed one at a time, and the committed patch of the step equals the net composition of the per-input patches: `net(p_{b+1} then … then p_{b+g})`. Revision boundaries between the batched inputs are lost, as a squash (Def. 4.9).
Status: **proved**, given T5 and the four premises below. The first version of this theorem stated none of them. The prototype violated the first two on one real input (D17) and the third on another (D21). The fourth was found by deriving the proof again at gate 1a: Def. 7.10 states the requirement and the theorem did not list it.

**Premises.**
- **B1 (one writer per telemetry key).** For every key (element, property, window start) of a telemetry sink, at most one row reaches the sink per window close. Group equality must therefore be the same equality as the key of the emitted element, after canonicalization. A store that keeps the last value written makes the value depend on emission order, and emission order depends on chunking. Several rows that write one value for one key are one value with counted support, and the window stays while a row supports it. The intended behavior when the premise is broken is that of Def. 6.4: two different values for one key are a conflict, the window has no value and the conflict is reported; storing the greatest or the last value hides it.
- **B2 (late rows are a function of logical time).** A row for a window whose state has been dropped (beyond the late horizon, D9) is dropped and counted. It neither revises nor recreates the window. Whether a row is late depends only on its event time and the logical frontier at its recorded position, never on the batch it travelled in. A row that an operator derives while a logical-time advance is processed is judged against the frontier before that advance: the advance that closes a window does not make the rows derived from the closing late.
- **B3 (identity binding is independent of arrival order).** After any prefix of the recorded input, the identity of every element, as seen through `Rep`, is the same whatever the chunking. This holds when the representative of an entity is the smallest id minted for any key that denotes it, whether or not that key was used before (Proposition 1.8). Two weaker rules do not give it. With "first binding wins" and a counted conflict it holds only when no two keys of one entity reach the catalog in an order that depends on chunking. With a merge of only the ids already in use, the final id still depends on whether a key that nothing had used yet arrives before or after the key that resolved the entity. The engine had each of these rules in turn, and each was found by a digest that differed (D21).

- **B4 (a step is its inputs in order, where the semantics is a function of the sequence).** `Threshold` fixes the value of a window when it leaves the retained range, under the structure of that moment (Def. 7.10), so its state is a function of the recorded sequence and not of the integrated input (Theorem 6.1). Within one step, logical-time advances and the changes of structure around them must take effect on carried state in their recorded order. The first three premises make the rest of the state a function of the integrated input; this one covers the part that is a function of the sequence.
- *Known exception.* A telemetry property with combine `mean` or `last` on an element that can merge: the outcome of the merge depends on whether the rows arrived before or after the link (Law 7.5, remark). It is outside this theorem until that case is ruled.
- *Outside the statement.* Evidence histories (Def. 9.2) are defined from commits and so depend on the steps. The theorem is about graph state and telemetry.

*Proof.* (a) The engine consumes records in the recorded order and assigns the ingestion sequence per record. Batches are carriers, not transactions, and a malformed record is rejected without dropping the rest (ARCHITECTURE.md). So the sequence `ι` and the per-record results do not depend on chunking. (b) By Theorem 6.1, the output state after any prefix of inputs is `⟦P⟧(I(inputs))`, a function of the integrated state, hence the same for the batch and for the sequence. Consecutive committed patches compose (Theorem 3.1, Def. 4.2), and `net(p then q then …)` is `toPatch` of the signed delta between the two states (Theorem 4.8). The batch patch is this canonical net transition. Stateful operators consume closed windows in `windowStart` order within a step, so their fold is unchanged. A record rejected inside a batch is rejected individually, so the batch contains the same accepted records. Theorem 6.1 gives a function of the integrated state only for output that is a function of it. B1 makes the telemetry value of a key a function of the rows of its group, not of write order. B2 makes the set of rows that count for a window a function of logical time. B3 makes the identities of the emitted elements a function of the recorded sequence. B4 makes the carried state of a `Threshold` after a step the state after its inputs taken one at a time, which is the function of the sequence that Theorem 6.1 gives. Without them the output is a function of the integrated state and of the batch boundaries, and (a) fails. ∎

*Evidence for the premises.*
- **B1** is tested: `Two_spellings_of_one_resource_id_count_into_one_window_whatever_the_batching` (`BatchInvarianceTests.cs`) writes one resource under two spellings of its id in one batch, in two batches and in two batches in the other order, and asserts one window with the value 5. With the fix reverted (the group keyed by the raw id) all three cases fail (`paper/evidence/mutation-head6.txt`).
- **B2** is tested: `A_row_for_a_window_beyond_the_late_horizon_is_dropped_and_counted_and_never_replaces_what_was_emitted` (four cases of late rows and lateness) and, from the other side of the horizon, `A_row_for_a_window_inside_the_late_horizon_revises_it` (two cases). With the drop disabled the four cases fail and the two still pass.
- **B3** is tested on examples and on two captures, not in general. `IdentityMergeTests.cs` checks the merge laws and the survivor under all orders of three merges and of three keys (the candidates include the own ids of the keys). `BatchInvarianceTests.cs` has one synthetic input in two arrival orders (the pod row before the flows that name the pod, or after them, so that the flows bind a provisional identity and the pod row merges it) at chunk sizes 1, 2, 5 and 2,000 with equal digests, and it asserts that the merge count differs between the two orders, so the test is not vacuous. The replays of both captures at five chunk sizes give one digest each, with the same merge count at every size (35 and 43; Ch. 14, 14.5). No generator produces random key arrival orders and compares the final ids. Proposition 1.8 states the property with a sketch of its proof.
- **B4** is exercised by the differential harness, which cuts the log of every world at every position and compares with a reference that folds the sequence; whether one of its worlds puts a change of structure and an advance into one step is to be confirmed with the engine core session (test T-B4, [inventory.md](inventory.md)).
- B1 to B3 are also exercised together by every replay of a capture at several chunk sizes and by `LiveReproducibilityTests` with shuffled arrival and random flush points.

**Theorem 6.3 (replay determinism, T7).** The output log of a graph is a function of the recorded input sequence of its projection and the pinned definitions. Two runs from the same state with the same recorded sequence, the same definitions and the same logical-time controls produce equal commit records.
Status: **proved**, given the premises F1 (Theorem 3.5), Proposition 5.4 and Theorem 6.1.

*Proof.* Induction over the input sequence. The transition from state and input to the next state and commit is a composition of functions: (1) operator denotations are functions of Z-sets, which are unordered, and the serialization of the resulting edit set has a canonical order (Theorem 4.4); (2) expressions use the closed function set (Proposition 5.4), so they depend on row values only; (3) identity allocation is a pure function (Theorem 1.4) and resolution depends on the binding set, itself a function of earlier inputs (Theorem 1.5); (4) logical time enters only through `λ` inputs; (5) a conflict is resolved by a function of the fragment multiset (Def. 6.4) and a runtime fault is local to its row (Def. 5.19), so neither has an arrival-based tie-break and neither fails the event; (6) a `Fixpoint` is a bounded unrolling, a function of its input (Theorem 6.1), and what its bound cuts off is a function of the data; (7) telemetry enters only as closed-window records with sequence numbers and a pinned watermark (Def. 6.8, Theorem 7.3). Different projections may advance concurrently, but each consumes its own recorded sequence, which includes the graph-change inputs of upstream graphs at their recorded positions. The engine does not promise identical outputs for different interleavings of independent sources (ARCHITECTURE.md): the interleaving is part of the recorded input. ∎

**Theorem 6.4 (reconstruction and handoff, T8).** A consumer that takes a sealed snapshot of graph `g` at `r_s` and then applies the commit records `r_s + 1, r_s + 2, …` it receives, holds `G_r` after each, for every `r`. A scoped subscription (Def. 3.12) holds the scoped state. A snapshot followed by a squashed batch reconstructs only the final boundary.
Status: **proved** relative to the store assumptions of Ch. 11.

*Proof.* `G_r = apply(E_r, …apply(E_{r_s+1}, Snap(r_s)))` (Theorem 11.1(a)). The follower delivers exactly `r_s + 1, r_s + 2, …` in order, once each, or an explicit `Gap` (Theorem 11.5), so there is no handoff gap. A `Gap` requires a new snapshot and is never a successful partial reconstruction. A squashed batch is `net` of the composed patches (Def. 4.4), which maps the state at its `from` to its `to` and says nothing about intermediate states (Theorem 4.8). ∎

**Theorem 6.5 (recursion terminates at the least fixpoint, T9).** Let a `Fixpoint` body satisfy the admitted fragment (operators `Match`, `Filter`, `Map`, `Join`, `Union(requireEqual)`, `Distinct`, and `Traverse` with `minDepth ≤ 1` whose depth column is not read; no `IdOf`) and let the active domain be finite: every field of `R_rel` ranges over a finite set `A` (entities of the port `over`, values of the seed, literals of the program). Then `f` is monotone, the iteration reaches `lfp(f, seed)` in at most `|A|^k + 1` steps for rows of `k` fields, and `lfp` is the unique least fixpoint.
Status: **proved**, under the finite-domain condition F5 (stated in the remark below), by the ascending chain argument on a finite lattice; read only, checked by no tool. With `maxIterations ≥ |A|^k + 1` and `maxFacts ≥ |A|^k` evaluation never hits a limit. **What the engine guarantees is less:** its `Fixpoint` is an unrolling with a bound `max` between 1 and 64, so it always terminates, and it returns `lfp(f, seed)` only when the least fixpoint is reached within `max` steps. F5 is not checked, and the tests use acyclic inputs only. Wanted: test T-FIX ([inventory.md](inventory.md)).

*Proof.* Each admitted operator is monotone in set semantics: `Match`, `Join` and `Map` are unions of images of their input rows, `Traverse` without its depth column and with `minDepth ≤ 1` is the set of pairs at distance at most `maxDepth` (without the start itself for `minDepth = 1`), which only grows when edges are added (with a larger `minDepth`, or with the depth in the row, a new edge can shorten a distance and remove a row, so the operator is not monotone), `Filter` has a predicate that depends on a row only, `Distinct` and `Union(requireEqual)` act on sets. So `f` is monotone and extensive after `X ∪ f(X)`. The sets `f^n(seed)` form an ascending chain inside the finite lattice `2^{A^k}`, which stabilizes after at most `|A|^k` strict increases. The stable value is a fixpoint, and any fixpoint containing the seed contains every `f^n(seed)` by induction, so it is the least. ∎

*Remark (gap in [R03]).* The typing rule of `Fixpoint` requires entity fields to come from the finite port `over` but allows `Map` in the body, so an arithmetic field (a depth counter, `d + 1`) is not finite, and then only `maxFacts` and `maxIterations` bound the evaluation. F5 is a new proposed typing condition: assignments in a fixpoint body copy fields or use literals, or the program declares a bound domain. Without F5, Theorem 6.5 does not hold and the limits only turn non-termination into an atomic failure.

**Theorem 6.6 (retraction under recursion, T10).** (a) Re-evaluating the fixpoint of an affected stratum from the integrated inputs after any retraction is correct. (b) Support counting is not correct on cyclic derivations.
Status: (a) **proved** from Theorem 6.1, (b) **proved** by a counterexample; read only. Neither is tested on a cyclic input (test T-FIX). An earlier part (c), that efficient maintenance of recursive views under retraction is known, was a pointer to the literature and not a statement of this paper; it is now the remark after the proof. Its cost on the engine is not measured.

*Proof.* (a) By Theorem 6.1 the correct incremental output is `D ∘ ⟦P⟧ ∘ I`, and evaluation of `⟦P⟧` on the integrated state is the definition. (b) Take `r(a) ← base(a)`, `r(b) ← r(a)`, `r(a) ← r(b)`. With `base(a)` present, `r(a)` has support 2 (base and `r(b)`) and `r(b)` has support 1. Retracting `base(a)` leaves `r(a)` with support 1 and `r(b)` with support 1, both positive, although neither is derivable. The correct result is empty. ∎

*Remark (literature, not used).* Efficient maintenance of recursive views under retraction exists: DRed (delete and rederive) and counting for non-recursive views ([gupta1993]), and nested incremental evaluation with partially ordered versions ([mcsherry2013], [budiu2023] Section 5). The engine does not use them: its bounded unrolling is maintained operator by operator (Theorem 6.1).

**Proposition 6.7 (cross-graph telemetry reads are deterministic).** A `Series` over a graph port reads a set of closed windows that is a function of the frontier entry `gin[g'] = (r, tw)`.
Status: **proved** (Def. 6.8). This is the missing step of Theorem 7.3.

**Proposition 6.8 (stateful telemetry operators under revision).** For `Delta` and `Threshold`, the output after a revision of window `j` of key `k` is the fold over the revised sequence, so the emitted change is the difference of the key's outputs before and after.
Status: **proved** (Def. 6.7). Corrections can flip `status` at an earlier window than the one just closed. A revised window is therefore not silent. Late policy `reject` and `ignore` avoid corrections.

## 6.4 Incremental strategy per operator

Cost classes follow Fact 11.1 and Theorem 13.1; the strategy is the DBSP class ([budiu2023]).

| Operator | Strategy | State |
|---|---|---|
| `Filter`, `Map`, `Union`, emits, `Window` assignment | linear: apply to the delta batch | none |
| `Match` edges, `Join` | bilinear: new left against old right, then new right against the new left | adjacency or hash arrangement keyed by entity handle or join key |
| `Traverse` | per start element a breadth-first reach to the depth bound, recomputed only when a visited element or edge changed, only the difference emitted | visited set per start |
| `Group`, `Rollup` with `count`, `sum` | per-key accumulators updated by signed deltas | one per key (and window) |
| `Group`, `Rollup` with `min`, `max`, `mean`, `weightedMean`, `any`, `all`, `last` | per-key ordered multiset, or recompute the affected key | per key |
| `Distinct` | weight per row, emit on `0 ↔ positive` transitions | weight map |
| `Delta`, `Threshold` | per-key state machine over ordered closed windows | previous value or state and counters |
| `Fixpoint` (design) | semi-naive iteration on the delta, re-derivation of affected keys on retraction | relation plus support |
| `Fixpoint` (engine) | bounded unrolling of `distinct(R union step(R))` into `max` copies of the step, so every operator in it stays incremental; facts that need more than `max` steps are not derived, and `maxFacts` is recorded and not enforced | one `Distinct` and one step per level |
| `Series` | append-only scan of new closed windows, retraction of windows leaving `within` | cursor per key |

The hot path never touches the catalog graph. Activation interns ids, precomputes subtype bitsets, lays out columnar row batches, compiles expressions to a vectorized interpreter, fuses linear chains and chooses the strategy above ([R03] section 11.1). Ordered per-projection processing limits parallelism to pipelining inside a batch and to independent projections (Theorem 13.3). Partitioning one projection by entity handle with an ordered merge is open (Q16 of [R03]).

## 6.5 Example

Reachability as the admitted recursion: `R = seed ∪ π(R ⋈ E)`, where `E` is the relationship facts of type `DependsOn` and the active domain is the entities of the port `over`. Inserting `E(c, d)` into a state with `R ⊇ {(a, c)}` derives `(a, d)` by semi-naive iteration in one round. Retracting an edge on a cycle `a → b → a` that was the only support of both `r(a)` and `r(b)` is the case of Theorem 6.6(b): counting keeps both, re-derivation of the affected keys removes both.

## 6.7 Deviations found by the prototype

Ids refer to Ch. 14 (14.8).

- **D7.** Windows close inside the projection by `Group` over `Window` and by explicit `Advance` inputs, and replay recomputes closed windows from the raw rows. Closed-window records are not recorded inputs (Def. 7.7). Determinism holds in replay because the raw rows are the recorded input.
- **D9.** On a live source closed windows stay revisable for 3 window widths, then their state is dropped; a recorded capture, replayed or served, keeps 1,000,000 (Ch. 7, 7.7). Def. 6.7 and Prop. 6.8 have no horizon.
- **D11.** `Join`, `Traverse`, `Fixpoint`, `Values`, `Union`, `Distinct` and the aggregates `mean`, `weightedMean`, `any`, `all`, `last` are built, each with example tests that include retraction (`OperatorTests.cs`). `Delta` is not built. `Fixpoint` is a bounded unrolling with `max` levels, not the semi-naive iteration of Def. 6.9: Theorem 6.5 applies when `max` is at least the longest derivation, and a smaller `max` gives a prefix of the closure (the test with `max` 1 on a chain of four nodes derives 5 of the 6 pairs). Unrolling is acyclic, which is why the counterexample of Theorem 6.6(b) does not arise here. The tests cut and restore the middle edge of an acyclic chain. No test retracts on cyclic input, so 6.6(a) has acyclic evidence only. The health model uses `Traverse` to depth 16 for its reach (Ch. 7, 7.5) and not `Fixpoint`. `Join` has no cost measurement (H14).
- **D14 (fusion).** Fusion is by selection vectors and shared column arrays, not generated code. There is no IL or delegate compiler, only the vectorized interpreter (Q14).
- **D33 (resolved).** The engine evaluated `Threshold` over the windows in the look-back only, so a state changed because a window grew old. Since `ad83e63` it folds over the episode with a carried state (Def. 6.7, Def. 7.10), and the differential harness agrees with the reference evaluator.
- **D34 (resolved except for the report).** For conflicting fragments the engine let the last sink and, inside one sink, the last arrival win. Since `ad83e63` the outcome is the function of the fragment multiset of Def. 6.4, and conflicts are counted per run. A commit does not yet list its conflicts.
- **D17 (resolved): the premises B1 and B2.** On the first real capture, chunk size 50 gave a different state digest than the other sizes: one Activity Log telemetry window had the value 2 and not 3, and all graph states were equal. There were two causes. (1) The Activity Log writes one resource under two spellings of its id (`resourcegroups` and `resourceGroups`). The `Group` keyed by the raw text made two aggregates for one element and window, the telemetry store keeps the last one written, and so the value depended on emission order. That violates B1; the definitions now group by `lowerInvariant(resourceId)`. (2) A row for a window whose state had already been dropped, beyond the late horizon, created a new window that replaced the value emitted earlier. That violates B2; such a row is now dropped and counted. This paper found the difference and not the causes; the engine session found both. Since the fix the digest is equal at every chunk size (`paper/evidence/chunk-50-defect.txt` before, `replay-chunks-head.txt` after).
- **D21 (resolved in two steps): the premise B3.** After D17, chunk size 1 on the first capture still gave a different digest: eight `Calls` relationships of the master differed in one endpoint id, with their telemetry, and the identity counters differed (0 conflicts at chunk size 1, 6 at the larger sizes; `paper/evidence/chunk-1-defect.txt`). The cause was "first binding wins": which of two keys of one entity bound first depended on the chunking. Step one merged two identities that denote one entity. The digest was then equal at five sizes, but the number of merges still depended on the size (1 at 50 and above, 0 at 1; `replay-chunks-merge.txt`), a sign that the final ids were not yet independent of order. Step two made the representative the smallest id minted for any key of the entity (Proposition 1.8). Since then each capture has one digest and one merge count (35 and 43) at all five sizes (Ch. 14, 14.5). The ids of pods changed with each step, so digests from before and after a step are not comparable.
- **Quine invariant.** The T6 test checks that the integrated output equals the final graph and the output under other chunkings, on fixtures and the real capture. It is not a property over random operator sequences (O6.1 remains).
