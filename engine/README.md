# Sattle engine

Sattle loads typed definitions, replays recorded inputs or receives live rows, and maintains the graphs of an active space. The C# kernel runs on .NET 11. Every definition is a [gkql](#gkql) document: a module is `*.module.gkql.json`, a projection `*.gkql.json`. [Glossary](../paper/glossary.md)

For a small capture you can replay locally, follow one submission from its parent span to its two children. The walkthrough then uses the ingress receipt to correct a receiver rule in Canvas. The kiln example uses the same CLI to replay a health policy with entry, recovery and freshness thresholds. [Standard projections and walkthrough](standard/README.md)

## The three commands
```bash
sattle check [--defs DIR] [--update-pins] [--plan]
```
- Checks the non-hidden files directly in the selected definition directory. The CLI registers only the gkql reader (`Program.Projections`). Any other file in that directory is a load error (`UnreadFile`). Checked: the JSON of each document (a JSON error names line and column, a projection error the verb), K1 to K11, the typing judgments, release digests and import pins. Errors print as `file:line:col: error Code: message`. Exit 1 on errors.
- A GKQL `values` verb can hold a project’s rules. It declares column types and a `rows` array. An empty array yields an empty relation with those columns. The optional `key` names a Text column whose value must be nonblank and unique within the table. A space binds a graph or source by name and a scalar parameter with `{"lit": value}`. [Coverage rules table](standard/coverage/sattle.coverage.rules.gkql.json)
- `--update-pins` rewrites import digests in place (digests are computed, never typed). `--plan` shows the compiled plan: strategy per operator, fused chains, adapter contract check.
```bash
sattle replay CAPTURE [--space NAME] [--speed N] [--advance-every 60s] [--lateness 60s] [--chunk N] [--late-horizon WINDOWS] [--store memory|sqlite=PATH|cosmos=ENDPOINT[,db=NAME][,drop]] [--until RFC3339] [--out DIR]
```
- `CAPTURE` is a capture directory, `lab/fixtures`, or `latest` (newest under `lab/captures`). Records are merged in capture-time order. Each source's adapter turns them into rows. Explicit `Advance(λ)` controls are inserted when the capture clock crosses a step boundary: `λ = floor(capturedAt / step) * step - lateness`, so logical time is a recorded input and never the wall clock.
- `--speed N` plays N capture seconds per wall second (0, the default, is as fast as possible). `--chunk` sets rows per batch; it changes patch granularity, never the result (T6).
- `--store memory` (the default) keeps the head number of each graph and nothing else: the graphs are the engine's own, and nothing reads history from this store. `sqlite=` and `cosmos=` keep the whole history, and only they can be restarted from (`serve --store`).
- Prints records and rows per source, rejections, per graph revision, element counts per type and telemetry counts, the service tree with top dependencies, identity statistics, runtime faults, lost events and a state digest. `--out DIR` writes the canvas files.
```bash
sattle serve CAPTURE [replay options] [--port 5080] [--write-definitions] [--store sqlite=PATH|cosmos=ENDPOINT[,db=NAME]]
```
```bash
sattle serve --store sqlite=PATH [--port 5080]
```
```bash
sattle serve --live [--eh-namespace NS | --eh-resource-group GROUP] [--hub sattle-ingest] [--group '$Default'] [--from latest|earliest] [--seconds N] [--live-out DIR] [--store sqlite=PATH|cosmos=ENDPOINT[,db=NAME]]
```
- `serve` runs the space as a service. The wire contract is [PROTOCOL.md](PROTOCOL.md): definitions served as a graph (`catalog`) with the kernel as its ontology, `POST /check`, `POST /definitions/{module}` (re-activation), edits to editable graphs, subscriptions over one WebSocket, telemetry range reads, meters and thresholds, lineage. Replay input runs in the background at `--speed`.
- `--live` reads an Event Hub instead of a capture: Entra auth through the Azure CLI credential (no keys), the envelope of `lab/CAPTURE-FORMAT.md`, the record adapter as replay, logical time from the recorded `capturedAt`. With `--store` the run resumes after a kill: every envelope is journaled in the store with the position of the source after it (Event Hubs partition and sequence number) before it is processed, flushes are journaled too (so the chunks, and with them the revisions, are cut where the live run cut them), a restart reads the position back and continues after it, and an envelope delivered again is dropped by its delivery key (the last 20,000 keys survive the restart). Without `--store` there is no resume. Every consumed envelope is also recorded to `<live-out>/live/stream.ndjson`. The command prints the state digest when it stops. `sattle replay <live-out> --no-flush --late-horizon 3` reproduces it (add the same `--advance-every` and `--lateness` if the live run set them): the recording is one file in arrival order and is read in that order, the live run uses late horizon 3 where `replay` has none, and it does not flush at the end. The guarantee is tested on the fixtures and the captures with shuffled arrival order and random flush points (`LiveReproducibilityTests`). For each envelope the order is receive, journal (with the source position), record, process. The journal is the truth and is written first: a kill leaves at most one envelope that is journaled and not processed, and the next start processes it from the journal exactly once. The recording is written after the journal, so it never holds an envelope the journal lacks; a start that finds it shorter than the journal appends the missing envelopes before it reads the source. After a kill and a restart the recording, the journal and the digest agree (`LiveCrashTests` kills the run at each step and compares with an uninterrupted run). Without `--store` there is no journal, so a kill loses the envelope in flight and the recording is the only record. Run against the lab's hub (#70): the body is the envelope as a JSON string and is unwrapped. Ctrl-C, SIGTERM or `--seconds` stop the input through the server's lifetime: it finishes the envelope in hand, writes out its pending rows and prints why it stopped, the counts of this run, the position and the state digest, and the process ends after that line. An input that ends on its own (a source it cannot read, for example) stops the server too. `--from` is where a run starts when its store has no saved position; with one it continues after it, and any value other than `latest` or `earliest` is refused. Start the engine at `--from latest` before the forwarder (or restart the forwarder), so the forwarder's relist gives it the whole cluster; `--from earliest` reads the hub's 24 hours at the one throughput unit's egress (about 1.6 MB/s) and does not catch up. `lab/DEMO-LIVE.md` has the commands.
- `--write-definitions` writes committed definition edits back to the gkql documents (a projection the commit removes is deleted). It is refused when a definition is not the text of its file: a module replaced by an overlay (`--overlay`, or the local overlay of the captures). A commit writes every definition back, so the overlay would end up in the definitions folder.
- `serve --store X` takes a seal every `--seal-every` journal entries (default 5000): a snapshot of the whole state of the space (operator state, element layers, identity bindings, telemetry windows, hot graphs, served history, adapter state) stored next to the journal. A restart loads the latest seal, checks its state digest and catalog digest, and replays only the journal entries after it; a seal written by another build, or one whose digest does not match, is refused and the whole journal is replayed (slower, the same result). The restart prints what came from where: how many revisions and which graphs were loaded from the seal (not recomputed, digest checked against the seal), and how many journal entries were replayed and revisions recomputed. `--verify-journal` ignores seals: the whole journal is replayed, every recomputed commit is compared with the stored log, and the state at the seal position is compared with the seal's digest. `PERF.md` has the numbers (H10). `--no-seal` takes no seal and uses none at the start: the whole journal is replayed.
- `serve --store X` keeps a journal in the store (SQLite file or Cosmos database) next to the commit log, and a store that has one is restarted from it alone: `sattle serve --store sqlite=PATH` with no capture and no definitions directory replays the journal, recomputes every commit and compares it with the stored one, and serves the same sequence numbers, revisions, state digest and `/space` as before the stop ([PROTOCOL.md](PROTOCOL.md), "Version 3.5"). Restart cost is a replay of the journal, measured in `PERF.md` (H10). Not stored: drafts. A capture is not resumed.
- `sattle bench` runs the benchmarks of `PERF.md`; `sattle bench estate` the large-estate run.

## gkql
gkql is the one definition language: JSON documents that the reader (`src/Sattle.Gkql`) lowers to definition graphs. [Definitions](definitions/)
- **File kinds.** `MODULE.module.gkql.json` is a module document: `module`, `version`, `imports` (module, alias, version, pinned `digest`), `entities`, `relationships`, `identities` (identity domains: the key components that name an element), `equivalences`, `rows` (the row types of a source), `constraints`, and in a space module `space` (its sources and graphs). `MODULE.PROJECTION.gkql.json` is a projection document, one program: `graph`, `ontology` (the output module), `description`, `history`, `inputs` (a graph with its ontology, or a source with its row type and, both or neither, its `time` column and `lateness`: a row whose clock at arrival is beyond its time plus the lateness is left out and counted, and a window downstream stays revisable for the largest lateness upstream), `parameters`, `verbs`, `wires`, `rules`.
- **Wires.** A wire carries rows from a verb's output to a port of another verb (`in`, or `left` and `right` of a join). The verbs and wires of a program have no loop; recursion is a `fixpoint` (or a bounded `traverse`).
- **Placeholders** (expressions over the rows): `ref` (a column, or `d.name`: a property of the element in column `d`), `lit` (a constant), `param` (a parameter), `fn` with `args` (a function), `identity` with `args` (the element an identity domain names with these key components).
- **Functions** of `fn`: `==`, `!=`, `<`, `<=`, `>`, `>=`, `and`, `or`, `not`, `iff`, `coalesce`, `startswith`, `endswith`, `contains`, `concat`, `lower`, `trim`, `+`, `-`, `*`, `/`, `negate`, `todecimal`, `isnotnull`, `rate`, `shift` (moves an instant by a duration such as `"90s"`), `id` (the id of an element).
- **Verbs** that read:
  - `rows`: the rows of a source input.
  - `values`: constant rows with declared column types; an optional `key` names a Text column that is nonblank and unique.
  - `graph-match`: the matches of a pattern of nodes and edges in an input graph, one row each, one column per pattern variable. A property drawn on a pattern node is a value the node must have.
- **Verbs** that transform:
  - `where`: the rows whose `condition` holds.
  - `project`: only the named `columns`. `extend`: the input columns plus the named ones.
  - `union`: the rows of two or more inputs with the same columns.
  - `distinct`: each row once (set semantics over signed rows).
  - `join`: inner equi-join of `left` and `right` on the column pairs of `on`; the two sides share no column name.
  - `summarize`: one row per `by` key with `aggregates`: `count`, `countif`, `count_distinct`, `sum`, `min`, `max`, `avg`, `arg_max`, `arg_min` and `percentile` (`arg_max(order, value)`: the value of the row with the greatest order; `percentile(value, p)`, p a literal from 0 to 100: the value of nearest rank, no interpolation, a decimal without trailing zeros). Over telemetry windows `windowStart` stays a key and only `count`, `sum`, `min`, `max` and `avg` combine.
  - `window`: puts a row in the windows of its `time`: `period` long, one every `hop` (default: the period), so a row is in `period / hop` windows; adds `windowStart` and `windowEnd`. A late row revises its window.
  - `series`: the telemetry of the element in column `element`, read from an input graph over `lookback`: `property` (one metric) or `properties` (a list of metrics of the same element). `freshness`: after that long without a record the element is in no data. `fill`: the value of a window in which the source reported and the element did not.
  - `hysteresis`: a state per `by` key from the reading `value`: `high` after `enterAfter` readings above `above`, `low` after `exitAfter` readings below `below`, `initial` at the start, `noData` for no data. `aboveBy`, `enterBy`, `belowBy`, `exitBy` read a threshold or dwell from the row; `evidenceWindow` adds the `windowStart` that decided the state.
  - `retain`: a row leaves when the logical frontier passes its `time` plus `age`.
  - `traverse`: from the element in column `from`, every element reached over `min` to `max` edges of type `edge` (and its sub-types) in `direction` (`out`, `in`, `either`), one row each, in the new column `to`.
  - `fixpoint`: per node of its `in` rows (`key`, `value`) the least value of its equation, over the rows on its port `edges` (`from`, `to`): the greatest in `order` (a list of literals of the type of `value`, least first) of the node's own values and of the values of the nodes it depends on, each through the image list that `through` names for the edge's `by` value (one value of the order per value of the order, never going down). Cycles are allowed; no depth. One row per node with an `in` row and a value; a value outside the order is no value.
- **Verbs** that write (sinks):
  - `nodes`: one node per row; its `id` is an element column or an `identity`, its `props` are placeholders. With `extend` it adds properties to a node another sink makes.
  - `edges`: one edge per row between two end nodes given by id. `extend` adds properties to an edge another sink makes; `key` names the edge in its id when two sinks of one type join the same ends.
  - `link`: the two identities of a row name the same element, as an equivalence `policy` of the ontology allows (`assert` merges, `review` waits for a decision), with a `confidence` between 0 and 1.
- **Rules** (edit hooks): a sink names its `rule`; the program's `rules` list says what may be edited through it. `accept` (`create`, `delete`), `update` (the properties an update may change), `create` (`key`: the identity domain of a new element, `set`: its values), `delete` (`set`: what a delete sets instead of removing the element). A rule with none of them is `readonly`; an editable rule over the rows of a source is `bijective` (written back one for one), over graphs a `lens`.
- **Module properties**: `type`, `optional`, `label` (the property that names the element), `roles` (value to presentation role), `telemetry` (`temporality`, `combine`, `period`), `unit` (the unit of measure, for example `1/s`). Relationships also take `kind`, `hierarchy`, `rollup` and `super` (the relationship type this one is a sub-type of).
- **Parameters**: `name`, `kind`, `default`. A space binds another value in the graph's `inputs` with `{"lit": value}`.

## Keyed input records

A space can bind a row type to the `record` adapter. Send a capture envelope with `source` set to `records:<row type>`, a stable `payload.key`, and the row’s fields in `payload.values`. At a later `capturedAt`, new values replace the previous row for that source and key. Set `payload.deleted` to `true` to withdraw it. The row type can declare a Text field named `$recordKey` to read `payload.key` directly.

For coverage, give each distinct receipt its own key. Two receipts may refer to one task and role, even when they cite the same source reference. The graph preserves both receipts and counts the task once for that role. [Coverage input contract](standard/coverage/sattle.coverage.module.gkql.json)

## Canvas files and the seam
`replay --out DIR` and `serve --out DIR` still write static files in the layout of the canvas `StaticSource` (`manifest.json`, `space.json`, per graph ontology, snapshot, patches, telemetry). The records validate against `brainstorm/contracts/schemas` with the canvas' own ajv setup (the canvas repository's validation script is the command).

What the protocol changes against the first slice (details in PROTOCOL.md):
- Definition graphs are a served graph (`catalog`); `space.json` still carries stub projections for the static path, the protocol path does not need them.
- Telemetry has a range read, `windowStart` on every batch and live push. Ticks are still window ordinals, not revisions.
- `evaluate` is `POST /check` plus `POST /definitions/{module}`.
- The kernel ontology exports its `Any` value kind as `text` (the old `OntologyDefinition` has no `any`).
- Remaining mismatches: revisions are decimal strings in `{value}`; meter min and max come from replayed data; no correspondences file (lineage is its own endpoint); type and property ids are names, qualified when two modules share a name.
- Served history: the host keeps the last 2,000 patches per graph and the last 20,000 events (`--retain-patches`, `--retain-events`); an older request answers `410 Gap`, a subscriber resuming before them gets `gap`.

The Canvas coverage-review integration test previews and publishes a correction against a running engine. It reads the earlier graph revision and compares the published graph with an independent CLI replay. [Live coverage-review test](../canvas/tests/engine/coverage-review.test.ts)

## The host
`SpaceHost` (`Host.cs`, `Edits.cs`) holds the catalog and the engine under one lock and implements the protocol: served history per graph, re-activation, subscriptions, telemetry and lineage queries, edits.
- **Re-activation** (`POST /definitions/{module}`): the candidate catalog is built from the module texts with the edit (dependent pins re-sealed), checked, and compared with the current one. Then a fresh engine replays the retained input log once in order, and only the final difference per graph is emitted as one patch. Revision numbers continue after the old head. A no-op edit creates no revision. The input log keeps every row batch up to `HostOptions.InputRowCap` (40 M rows); beyond it re-activation answers `InputsNotRetained`.
- **Lineage** is recorded per emitted element at the sinks: the element variables of the last contributing row (pattern variables of the `Match`), the sink, the rule, the operator chain. Elements from an aggregation carry only the element variables in the group key.
- **Edits**: `lens` and `bijective` rules (the `accept`, `update`, `create` and `delete` of a gkql rule are read, lowered and checked, P5). An edit of a derived graph becomes a proposal on the graph that ingests the edited type (`authored` for capabilities) by the owning rule, then authored rows by the bijective inverse of the ingestion rule, is evaluated forward on a staged engine, and is accepted only if the staged graph equals the edited graph on the elements the lens rules own (PutGet). Accepted rows are recorded input. Rejections are typed (`NotEditable`, `ReadOnlyByRule`, `TelemetryNotEditable`, `NotAccepted`, `StaleBase`, `PutGetViolation`, `AmbiguousKey` (an update or delete of an element with two keys in its emit's domain), `ConstraintViolation`, `KeyMismatch`, `BadEdit`) and leave everything unchanged.
- The inverse of the ingestion rule is derived from its shape: one entity sink and one relationship sink over one authored rows port. Other shapes are `NotEditable`.

## Hot graph layout
`Graph` (`Graph.cs`) is the second layout of the hot graph, see `PERF.md`: `sattle bench` prints the memory line (managed heap of the hot graph for 750,000 entities and 2.5 M relationships; the numbers and the method are in `PERF.md`). `ReferenceGraph` in the tests is the first layout; `HotGraphTests` compares them on random edit sequences.

Graph matches run serially by default (`SATTLE_PREPARATION_WORKERS=1`). A higher limit lets workers scan separate ranges of a large graph patch. The writer joins their rows in patch order before the next operator runs. [Read the design and replay measurements](PERF.md#parallel-preparation-of-graph-matches).

## What exists
- Definitions: 19 gkql documents in `definitions/`. 13 module documents: the ontology modules `sattle.infra`, `sattle.cloud`, `sattle.doc`, the row types `sattle.source.{platform,flowlog,cloud,metrics}`, `acme.ops` (Example 1: instances and their placement, services, units, endpoints, hosts, flows, warning events, cloud resources, activity and audit events, flow logs, host and resource metrics, authored capabilities), `acme.svc` (Example 2: services, service groups, dependencies with flow telemetry and hysteresis status), `acme.biz` (Example 3, the lens), `acme.readiness` (Example 5, below), `acme.report` (the readiness report) and the space `acme.space` (6 graphs). 6 projection documents, one per file `MODULE.PROJECTION.gkql.json`: `acme.ops.ingest`, `acme.ops.authored`, `acme.svc.serviceDeps`, `acme.biz.capabilityView`, `acme.readiness.readiness`, `acme.report.readinessReport`. Changing a definition needs no rebuild.
- Version 3 of the protocol (see [PROTOCOL.md](PROTOCOL.md)): one ordered event stream with `seq` and resume, revision-addressed resources revalidated by a strong content ETag (only `/releases/{digest}` is immutable), the palette, drafts with 99-step undo by inverse patches, releases, preview.
- Rule classes: `readonly`, `bijective`, `lens` (checked for direction). A gkql rule's `accept`, `update`, `create` and `delete` decide the class ([gkql](#gkql)). `sync` is not built.
- Operators, each with the gkql verb that writes it: `Match` (`graph-match`: node and edge patterns, no quantified paths), `Filter` (`where`), `Map` (`project`, `extend`; the function `shift` moves an instant by a fixed duration), `Window` (`window`: windows `period` long, one every `hop`, a row in each of the `period/hop` that hold it), `Group` (`summarize` over rows: `count`, `countif`, `count_distinct`, `sum`, `min`, `max`, `avg`, `arg_max`, `arg_min`; closing windows by logical frontier, a late row revises its window), `Series` (`series`), `Rollup` (`summarize` over telemetry windows: `count`, `sum`, `min`, `max`, `avg`), `Threshold` (`hysteresis`), `Union` (`union`: signed rows of the inputs, same columns), `Distinct` (`distinct`: set semantics over signed rows), `Retain` (`retain`: a row is withdrawn when the logical frontier reaches its time plus the age, so evidence ages out of the master; a row already that old on arrival never passes), `Values` (`values`: constant rows, emitted once when the graph first evaluates), `Join` (`join`, kind inner: equi-join of two data inputs, bilinear delta over per-side hash indexes), `Fixpoint` (`fixpoint`: the least solution per node; a change evaluates only the nodes that reach a changed node, from no value up), `Traverse` (`traverse`: a bounded path from a start element, per start element the depth each element was first reached at; an added edge lowers depths from its far end, a lost edge walks its starts again), `EmitEntity` (`nodes`), `EmitRelationship` (`edges`), `Link` (`link`).
- Incremental strategy per operator (`check --plan` prints it): linear via selection vectors and shared columns, per-key accumulators with signed weights, bilinear delta for `Match` and `Series`, per-key state machines for `Threshold`.
- Silence (Def. 7.14 to 7.16, [PROTOCOL.md](PROTOCOL.md) "Version 3.18"): a `series` with `fill` holds that value for every window in which the source of the property reported and the element existed, so a covered silence is a record and ends a state; with `freshness`, an element without a record for longer than that is in no data, which `hysteresis` gives as its `noData` label. The replay and the live input record how far each source has reported (every envelope of an adapter counts for its sources). A window with a loss mark is not covered and holds no fill. Example: [`fill-and-no-data`](tests/Sattle.Differential/worlds/fill-and-no-data/w.view.v.gkql.json).
- Batch invariance: the state digest does not depend on the chunk size (`dotnet test --filter FullyQualifiedName~BatchInvarianceTests` on the fixtures; the full run adds every capture present at chunk sizes 1, 50 and 100000). The telemetry windows that differed at chunk size 50 had two causes, each a unit test (`BatchInvarianceTests`: two spellings of one resource id in one batch and in two batches in both orders, and a row beyond the late horizon). (1) The Activity Log writes one resource under two spellings of its id (`resourcegroups` and `resourceGroups`); the Group keyed by the raw text made two aggregates for one element and window and the telemetry store keeps the last one written, so the value depended on emission order. The definitions now group by `lowerInvariant(resourceId)`. The premise of the batch-invariance theorem that the input violated: each element and window is written by exactly one group row. (2) A row for a window whose state was already dropped (beyond the late horizon) created a new window that replaced the value emitted earlier; it is now dropped and counted (`late rows dropped`). Late horizon: none for a recorded capture, replayed or served; 3 window widths for a live source; `--late-horizon WINDOWS` sets one.
- Stores: in-memory, SQLite and Cosmos DB for NoSQL behind the six-operation port, one conformance suite parametrized over all three; in-memory telemetry ring behind the telemetry port.
- Cosmos store (`src/Sattle.Cli/CosmosGraphStore.cs`): `sattle replay CAPTURE --store cosmos=ENDPOINT[,db=NAME][,drop]`. Containers `log`, `state`, `identity`, `leases`, hierarchical partition keys led by tenant and graph. The commit point is the creation of the commit record in one transactional batch (a create answers 409 when the revision exists: the conditional write); a commit above the 2 MB limit writes its edits as chunk items `p:{r20}:{i}` first, and the commit record that names them is created last, so it stays the single commit point (chunks without a commit record are not a commit and are overwritten by the retry). Materialization into `state` is idempotent. One writer per graph: a lease item in `leases` (30 s, renewed at half, released on dispose) refuses a second writer even with the right head. Authentication: Entra (`DefaultAzureCredential`) for a real account; the emulator's well-known local key is used only when the endpoint is a loopback address; no key is read from any file. Emulator (vNext preview, http, gateway mode) limits: it supports hierarchical partition keys and transactional batch, and it reports a request charge of 1 per request, so request counts are exact and RU figures are not (`PERF.md`). Materialization writes one transactional batch per logical partition touched by a commit (the version rows and adjacency rows of an entity share a partition; the mirror knows where each version began, so there is no read before the write and a closed interval is replaced by id); a retry after a crash falls back to the idempotent per-edit path. Identity bindings go in one batch per domain partition, and the watermark every 64 commits. The `lens` container of the schema is not created: nothing uses it. Not built: a snapshot above 2 MB per element (an element state is one item).
- Identity merge (Theorem 1.7): the identity of an entity is the smallest id minted for any key that denotes it, whether or not that key was resolved before. When a `Link` binds a key to an entity, the key's own id is a candidate; if it is smaller or the key was already bound to another identity, the loser gets an additive forwarding record, `Rep` follows the chain, bindings stay immutable, and the engine remaps what it emitted under the loser (the master graph gets a patch that moves the loser's relationships to the survivor, the telemetry windows of re-keyed relationships move with them, derived graphs follow through their deltas). The final ids therefore do not depend on the order in which keys are bound (`BatchInvarianceTests`, `IdentityMergeTests`). `sattle replay CAPTURE` prints the `identities:` line (minted, aliased, merged, conflicts); a capture that had `Link` conflicts before the merge has 0 of them now, and the merges are mostly pods whose name key mints a smaller id than their uid.
- Evidence retention (turn 7): evidence elements (`ActivityEvent`, `WarningEvent`, `AuditEvent` and what derives from them) grew without bound; on a capture they are almost all of the master (`sattle replay CAPTURE` prints the master's entity counts by type on the line after `graph master`: add `ActivityEvent`, `WarningEvent` and `AuditEvent` and compare with the entity count). Each evidence rule of `acme.ops.ingest.gkql.json` now reads its rows through a `retain` verb with `age` 24h: an element stays while the logical frontier is less than its event time plus 24 hours. The rule is text in the definitions, the operator is generic, and the retained state is a function of the frontier (tested at chunk sizes 1 to 100000 on the fixtures and on every capture present, `RetentionTests`). To see the effect on a capture, replay it with another age: copy `definitions`, change each `"age": "24h"` to `"10m"` in `acme.ops.ingest.gkql.json`, run `sattle check --defs COPY --update-pins`, then `sattle replay CAPTURE --defs COPY`, and read the master line again. Not retained: the identity binding table (append-only by Theorem 1.5), the interner, the journal, and the retained input rows of a host. A design alternative that was not taken: a `retain` on the entity type of the ontology, which would have made the engine remove elements by a second mechanism next to the support counts; an operator reuses the retraction that every derived element already follows.
- Serving a capture is a replay: `serve CAPTURE` and `replay CAPTURE` use the same late horizon (none: every closed window stays revisable while its telemetry is retained; `--late-horizon N` sets one for both) and end in the same state digest (`ServeReplayTests`: estate, `lab/fixtures`, the newest capture). Only `serve --live` keeps 3. The horizon is stored with the journal and the seals.
- References: a relationship whose endpoint is not in the graph is served with the endpoint explained (`extent.references` of the snapshot, `danglingBy` of `GET /space`; [PROTOCOL.md](PROTOCOL.md) "Version 3.11"): `inOtherGraph` with the graph named, or `absent` with the key the id was minted from.
- Lineage: `GET /graphs/{g}/lineage` is complete for lifted elements (every row that supports an element, and every row of a `Group` an element is emitted from, paged), `GET /graphs/{g}/lineage/reverse` answers which higher elements an element is part of, and `replay --out` writes both and the rendered documents ([PROTOCOL.md](PROTOCOL.md) "Version 3.11", `LineageTests`).
- Document projections: a document is a derived graph of `sattle.doc` `Block` entities; one generic renderer gives deterministic Markdown with a digest per revision, served by `GET /graphs/{g}/document` ([PROTOCOL.md](PROTOCOL.md), "Version 3.4"). Worked example: `definitions/acme.report.readinessReport.gkql.json`, graph `readinessReport` (counts and one line per Unit of `readiness`).

## Edge lifting: a graph that abstracts the graph below it, edges included
- **Definition.** A level maps the nodes of the graph below to nodes of its own, the image `f(n)`: an instance to its service, a service to the capability that realizes it. The edges of the level are the quotient of the edges below: for every edge `a -> b` below with images on both ends, the level has the edge `f(a) -> f(b)`. Nodes and edges are lifted together, so a level never has nodes that the edges below cannot reach.
- **Self-loops** (`f(a) == f(b)`): not lifted. Traffic inside one image is not a dependency between images.
- **Parallel edges** (several edges below with the same pair of images): one edge, key `f(a) -> f(b)`. Its counters are summed (`sum` over the windows of all edges below), a ratio is recomputed from the sums and never summed or averaged, and a state is derived again from the aggregate by the same threshold, so the state of the lifted edge is the state of the traffic it carries, not the worst of its parts.
- **A node with several images** (a service that realizes two capabilities): `Realizes` is declared 0 .. 1 per source, so the ontology flags it, and the projection states a policy: the node is not lifted (nothing is counted for two images). Chosen over splitting (fractional counts) and a first-by-order pick (order is not defined on handles); an instance that backs two services is the one exception, it counts for each (`Backs` is not a function). Tests: `A_service_with_two_images_is_not_lifted_the_declared_cardinality_reports_it_and_no_call_is_counted_twice`.
- **Composition.** Two lifts equal the one-step lift from the bottom (`The_composition_of_two_lifts_gives_the_same_edges_and_sums_as_the_one_step_lift_from_the_instances`), and the ratio and state of a lifted edge are those of the summed counts (`The_ratio_of_a_lifted_edge_is_recomputed_from_the_summed_counts_and_its_state_follows_the_aggregate`).
- **Ends without an image** (a service that realizes no capability, a retired capability): the edge is not lifted. The inner join drops it; nothing is invented, and there is no catch-all node.
- **How it is written.** With joins, in the gkql projections `acme.svc.serviceDeps.gkql.json` and `acme.biz.capabilityView.gkql.json`: `graph-match` the edges below, `join` each end with the mapping from a node to its image, drop the pairs whose two images are equal (`where`), write one relationship per pair of images (`edges`), and roll the telemetry of the edges below up per pair and window (`series`, then `summarize`). A node with several images is left out by a join with the number of images per node (`capabilityView`), or counts for each image without that join (`serviceDeps`). Until Version 3.39 (PROTOCOL.md) the engine's own notation had a statement `lift` for this pattern; it was lowered to these steps and is gone.
- **Example (estate).** Instances and their `Calls` in the master; `serviceTree`: services with `DependsOn` web to api and api to db (flows, drops, ratio, state); `capabilities`: Storefront, Ordering, Data platform with `DependsOn` Storefront to Ordering and Ordering to Data platform, `callFlows` equal to the service-level `flows`, under the `Under` hierarchy (Commerce above Storefront and Ordering).
- **Authored capabilities in a capture.** [Keyed input records](#keyed-input-records) of the row types `acme.ops.CapabilityRow` (`capId`, `name`, `owner`, `status`, optional `parentId`; status `retired` retires it) and `acme.ops.RealizesRow` (`capId`, `site`, `namespace`, `service`), sources `records:CapabilityRow` and `records:RealizesRow` in the estate.
- **Tests.** `ProjectionEdgesTests` (the properties): every graph of the space whose output ontology declares relationship types has relationships on the estate (the exemption, with its reason: the document `readinessReport`); the lifted flows equal the service flows; the policies (self-loop, parallel edges, no image, retired capability) on variants of the estate; the static space written by `replay --out` has the edges in the final snapshot and the patches.

## Example 5: readiness, presentation roles
- `acme.readiness` is the ontology module (`Workload` with `replicas`, `readyInstances` and `state`, `Talks` between workloads with `state`) and `acme.readiness.readiness.gkql.json` the projection, bound in `acme.space` as the graph `readiness`.
- Per Unit it counts the ready instances of the master graph (every Unit contributes a zero row, every ready instance it controls a one, so a Unit with no ready instance still has a state) and sets `state` to `Ready` when the count exceeds the parameter `minReady` (default 0; a space binds another value with `{"lit": n}`), else `NotReady`. `Talks` joins two Units whose instances call each other; its `state` is `NotReady` when either end is, by two joins.

- Tested (`ReadinessTests`, parametrized over `minReady`) on the synthetic fixture `tests/Sattle.Tests/fixtures/deploy-health`: the state of a Unit follows its ready instances by patches in both directions, and the edge follows its ends.

## Deviations from the research documents
- **Revisions and wire**: as accepted in research 01. Integers on the wire are strings. Instants are nanoseconds in a signed 64-bit integer (1678 to 2262), decimals are .NET `decimal` (28 digits), not unbounded.
- **Kernel**: `Correspondence.source` and `.target` are named `sourceRefs` and `targetRefs`, because section 2.3 gives them kind `L<T>` while `Assign.target` is `T` and one property name keeps one kind per module. Canonicalizers `LowerInvariant` and `Trim` are separate function nodes (`canon.LowerInvariant`) from the scalar functions of the same name. A `NoType` relationship type and `NoType` entity type exist in `K`. Single-child slots use the segment `slot:#0`.
- **Release digest**: formula of section 2.9. Adapters declare a row-contract shape, not a digest, so a definition change needs no rebuild; activation compares shapes.
- **Identity**: no `Key`, `Identity` or `Evidence` graph nodes. Bindings are an append-only table in the identity catalog, written with the commit of the master graph (SQLite `identity_binding`). Two identities are merged by an additive forwarding record (see "What exists"); a `Link` conflict is now only a key already bound to an identity of a different type. Entity ids are `e:` plus 26 base32 characters of SHA-256 over the JCS of `[tenant, domain, component encodings]`. Relationship ids hash `[tenant, output ontology module, key rule, source id, target id]`.
- **Telemetry**: windows are closed inside the projection by `Group` over `Window` and by the explicit frontier. Closed-window records are not recorded as separate inputs (Def. 7.7); replay recomputes them from the raw rows, which is deterministic. The port gains `MarkPartial` and a `Deleted` flag on samples (window retraction), both on the ingest side.
- **Storage port** is synchronous. Identity bindings and the frontier travel in the commit batch as specified; `Follow` returns a list, not a stream.
- **Property tests**: seeded generators in xunit theories, 4,000 generated cases per property of Theorems 4.1 to 4.8 and the Ch. 3 invariants, not FsCheck (one dependency fewer, same reproducibility by seed).
- **Benchmark**: Stopwatch and GC counters, not BenchmarkDotNet. No IL or delegate compiler: only the vectorized interpreter exists.
- **Fusion** is by selection vectors and shared column arrays, not generated code.
- **Late data**: a closed window stays revisable for the late horizon (`EngineOptions.LateHorizonWindows`: 3 window widths for a live source, none for a recorded capture), then its state is dropped.
- **Columns after aggregation**: `v.p` read columns are not carried past `Group`, `Rollup` or `Threshold`; reading one there is a type error. Property reads must happen before grouping.

## Not done, or not verified
- Sources: the engine reads one envelope, keyed records (`records:<RowType>`, [lab/CAPTURE-FORMAT.md](../lab/CAPTURE-FORMAT.md)). Collectors outside the engine turn a source system into records (#147).
- Not built: `sync` rules, `Delta`. `--live` reads one hub (`sattle-ingest`) of one partition; the `eventhub/` capture files mirror the direct sources and are skipped by `replay`.
- Operators missing: `Delta` (no property in the definitions or captures is cumulative, so it would ship without data to test against) and rule class `sync` (triple graph grammar rules need the stored correspondence graph and the FWD and BWD translators of [Ch. 8](../paper/ch08-sync-direction-and-bidirectional-consistency.md), none of which exist). Both stay `supported: false` in `/palette` with the reason. They parse or check to a typed error with a position.
- Q5 (pod name reuse) was not evaluated; a flow that names a pod before the pod row arrives mints a provisional identity and the pod row then merges it.
- Whole-engine memory at the 240,000-pair estate is far over the hot graph's (`sattle bench estate` prints both: heap after structure and at the end, against the hot graph's `sattle bench` memory line); H5, H7, H8, H10 are measured in `PERF.md` with what each still needs on real hardware.
- Event time of Hubble flows is not monotone (the capture starts with history); late rows revise their windows, covered by a test, and the real capture produced no dropped rows.
