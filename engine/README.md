# Sattle engine

A deterministic graph transformation engine, first slice. Compiled kernel in C# (.NET 10) that loads ontologies, identity domains and projections as typed definition graphs from `.sattle` text, replays recorded lab data into a master graph, derives a service dependency tree with telemetry, and serves both to the canvas.

## The three commands
```bash
sattle check [--defs DIR] [--update-pins] [--print MODULE] [--plan]
```
- Parses and checks every `.sattle` file in `definitions/`: syntax with positions, K1 to K11, the typing judgments, release digests and import pins. Errors print as `file:line:col: error Code: message`. Exit 1 on errors.
- `--update-pins` rewrites import digests in place (digests are computed, never typed). `--print` shows the canonical printed form. `--plan` shows the compiled plan: for each `lift` statement the operators it was lowered to (`dependsOn: Lift Calls through Backs to DependsOn (images each), lowered to 15 operators: ...`), strategy per operator, fused chains, adapter contract check.
```bash
sattle replay CAPTURE [--space NAME] [--cluster NAME] [--speed N] [--advance-every 60s] [--lateness 60s] [--chunk N] [--late-horizon WINDOWS] [--store memory|sqlite=PATH|cosmos=ENDPOINT[,db=NAME][,drop]] [--until RFC3339] [--out DIR]
```
- `CAPTURE` is a capture directory, `lab/fixtures`, or `latest` (newest under `lab/captures`). Records are merged in capture-time order. Each source's adapter turns them into rows. Explicit `Advance(λ)` controls are inserted when the capture clock crosses a step boundary: `λ = floor(capturedAt / step) * step - lateness`, so logical time is a recorded input and never the wall clock.
- `--speed N` plays N capture seconds per wall second (0, the default, is as fast as possible). `--chunk` sets rows per batch; it changes patch granularity, never the result (T6).
- Prints records and rows per source, rejections, per graph revision, element counts per type and telemetry counts, the service tree with top dependencies, identity statistics, runtime faults, lost events and a state digest. `--out DIR` writes the canvas files.
```bash
sattle serve CAPTURE [replay options] [--port 5080] [--write-definitions] [--store sqlite=PATH|cosmos=ENDPOINT[,db=NAME]]
```
```bash
sattle serve --store sqlite=PATH [--port 5080]
```
```bash
sattle serve --live [--eh-namespace NS | --eh-resource-group GROUP] [--hub sattle-ingest] [--group '$Default'] [--from checkpoint|latest|earliest] [--seconds N] [--live-out DIR] [--cluster NAME] [--store sqlite=PATH|cosmos=ENDPOINT[,db=NAME]]
```
- `serve` runs the space as a service. The wire contract is [PROTOCOL.md](PROTOCOL.md): definitions served as a graph (`catalog`) with the kernel as its ontology, `POST /check`, `POST /definitions/{module}` (re-activation), edits to editable graphs, subscriptions over one WebSocket, telemetry range reads, meters and thresholds, lineage. Replay input runs in the background at `--speed`.
- `--live` reads an Event Hub instead of a capture: Entra auth through the Azure CLI credential (no keys), the envelope of `lab/CAPTURE-FORMAT.md`, the same adapters as replay, logical time from the recorded `capturedAt`. With `--store` the run resumes after a kill: every envelope is journaled in the store with the position of the source after it (Event Hubs partition and sequence number) before it is processed, flushes are journaled too (so the chunks, and with them the revisions, are cut where the live run cut them), a restart reads the position back and continues after it, and an envelope delivered again is dropped by its delivery key (the last 20,000 keys survive the restart). Without `--store` there is no resume. Every consumed envelope is also recorded to `<live-out>/live/stream.ndjson`. The command prints the state digest when it stops. `sattle replay <live-out> --no-flush --late-horizon 3 --cluster NAME` reproduces it (add the same `--advance-every` and `--lateness` if the live run set them): the recording is one file in arrival order and is read in that order, the live run uses late horizon 3 where `replay` defaults to 1,000,000, and it does not flush at the end. The guarantee is tested on the fixtures and the captures with shuffled arrival order and random flush points (`LiveReproducibilityTests`). For each envelope the order is receive, journal (with the source position), record, process. The journal is the truth and is written first: a kill leaves at most one envelope that is journaled and not processed, and the next start processes it from the journal exactly once. The recording is written after the journal, so it never holds an envelope the journal lacks; a start that finds it shorter than the journal appends the missing envelopes before it reads the source. After a kill and a restart the recording, the journal and the digest agree (`LiveCrashTests` kills the run at each step and compares with an uninterrupted run). Without `--store` there is no journal, so a kill loses the envelope in flight and the recording is the only record. Unverified against real Event Hubs (fake source only).
- `--write-definitions` writes committed definition edits back to the `.sattle` files.
- `serve --store X` takes a seal every `--seal-every` journal entries (default 5000): a snapshot of the whole state of the space (operator state, element layers, identity bindings, telemetry windows, hot graphs, served history, adapter state) stored next to the journal. A restart loads the latest seal, checks its state digest and catalog digest, and replays only the journal entries after it; a seal written by another build, or one whose digest does not match, is refused and the whole journal is replayed (slower, the same result). The restart prints what came from where: how many revisions and which graphs were loaded from the seal (not recomputed, digest checked against the seal), and how many journal entries were replayed and revisions recomputed. `--verify-journal` ignores seals: the whole journal is replayed, every recomputed commit is compared with the stored log, and the state at the seal position is compared with the seal's digest. `PERF.md` has the numbers (H10).
- `serve --store X` keeps a journal in the store (SQLite file or Cosmos database) next to the commit log, and a store that has one is restarted from it alone: `sattle serve --store sqlite=PATH` with no capture and no definitions directory replays the journal, recomputes every commit and compares it with the stored one, and serves the same sequence numbers, revisions, state digest and `/space` as before the stop ([PROTOCOL.md](PROTOCOL.md), "Version 3.5"). Restart cost is a replay of the journal, measured in `PERF.md` (H10). Not stored: drafts. A capture is not resumed.
- `sattle bench` runs the benchmarks of `PERF.md`; `sattle bench estate` the large-estate run.

## Canvas files and the seam
`replay --out DIR` and `serve --out DIR` still write static files in the layout of the canvas `StaticSource` (`manifest.json`, `space.json`, per graph ontology, snapshot, patches, telemetry). The records validate against `brainstorm/contracts/schemas` with the canvas' own ajv setup (the canvas repository's validation script is the command).

What the protocol changes against the first slice (details in PROTOCOL.md):
- Definition graphs are a served graph (`catalog`); `space.json` still carries stub projections for the static path, the protocol path does not need them.
- Telemetry has a range read, `windowStart` on every batch and live push. Ticks are still window ordinals, not revisions.
- `evaluate` is `POST /check` plus `POST /definitions/{module}`.
- The kernel ontology exports its `Any` value kind as `text` (the old `OntologyDefinition` has no `any`).
- Remaining mismatches: revisions are decimal strings in `{value}`; meter min and max come from replayed data; no correspondences file (lineage is its own endpoint); type and property ids are names, qualified when two modules share a name; the history is never trimmed, so `gap` messages exist in the protocol but the server never has to send one.

## The host
`SpaceHost` (`Host.cs`, `Edits.cs`) holds the catalog and the engine under one lock and implements the protocol: served history per graph, re-activation, subscriptions, telemetry and lineage queries, edits.
- **Re-activation** (`POST /definitions/{module}`): the candidate catalog is built from the module texts with the edit (dependent pins re-sealed), checked, and compared with the current one. Then a fresh engine replays the retained input log once in order, and only the final difference per graph is emitted as one patch. Revision numbers continue after the old head. A no-op edit creates no revision. The input log keeps every row batch up to `HostOptions.InputRowCap` (40 M rows); beyond it re-activation answers `InputsNotRetained`.
- **Lineage** is recorded per emitted element at the sinks: the element variables of the last contributing row (pattern variables of the `Match`), the sink, the rule, the operator chain. Elements from an aggregation carry only the element variables in the group key.
- **Edits**: `lens` and `bijective` rules (`accept`, `on create key ... default`, `on delete set|remove` are parsed, printed, lowered and checked, P5). A view edit becomes a master proposal by the owning rule, then authored rows by the bijective inverse of the ingestion rule, is evaluated forward on a staged engine, and is accepted only if the staged view equals the edited view on the elements the lens rules own (PutGet). Accepted rows are recorded input. Rejections are typed (`NotEditable`, `ReadOnlyByRule`, `TelemetryNotEditable`, `NotAccepted`, `StaleBase`, `PutGetViolation`, `AmbiguousKey` (an update or delete of an element with two keys in its emit's domain), `ConstraintViolation`, `KeyMismatch`, `BadEdit`) and leave everything unchanged.
- The inverse of the ingestion rule is derived from its shape: one entity sink and one relationship sink over one authored rows port. Other shapes are `NotEditable`.

## Hot graph layout
`Graph` (`Graph.cs`) is the second layout of the hot graph, see `PERF.md`: `sattle bench` prints the memory line (managed heap of the hot graph for 750,000 entities and 2.5 M relationships; the numbers and the method are in `PERF.md`). `ReferenceGraph` in the tests is the first layout; `HotGraphTests` compares them on random edit sequences.

## What exists
- Definitions: `definitions/*.sattle`, seventeen modules (among them `acme.deployhealth`, the estate tree `acme.tree`, `acme.treehealth`, `acme.treereport`, and the reports): `sattle.infra`, row contracts `sattle.source.{k8s,hubble,azure,prometheus}`, `sattle.azure`, and `acme.ops` (Example 1: pods and their placement, services, endpoints, nodes, Hubble flows, Kubernetes warning events, Azure Resource Graph resources, VNet flow logs, Prometheus node metrics, Azure Monitor metrics, authored capabilities), `acme.svc` (Example 2: services, namespace groups, dependencies with flow telemetry and hysteresis status), `acme.biz` (Example 3, the lens), `acme.workload` (Example 4, below), `acme.space` (the graph space). Changing a definition needs no rebuild.
- Version 3 of the protocol (see [PROTOCOL.md](PROTOCOL.md)): one ordered event stream with `seq` and resume, revision-addressed resources revalidated by a strong content ETag (only `/releases/{digest}` is immutable), the palette, drafts with 99-step undo by inverse patches, releases, preview, refactoring.
- Rule classes: `readonly`, `bijective`, `lens` (with `accept`, `on create`, `on delete`). `sync` is not built.
- Operators: `Match` (node and edge patterns, no quantified paths), `Filter`, `Map`, `Window`, `Group` (`count`, `countDistinct`, `sum`, `min`, `max`, `mean`, `weightedMean(value, weight)`, `any`, `all`, `last(value, order)`; closing windows by logical frontier with `ignore`, `revise`, `reject`), `Series`, `Rollup` (`sum`, `min`, `max`, `mean` over gauges), `Threshold`, `Union` (`union a, b`: signed rows of both inputs, same columns, conflict policy `preserveEvidence` only), `Distinct` (`|> distinct`: set semantics over signed rows), `Retain` (`|> retain on time for 24h`: a row is withdrawn when the logical frontier reaches its time plus the age, so evidence ages out of the master; a row already that old on arrival never passes), `Values` (`values { a: 1 }, { a: 2 }`: constant rows, emitted once when the graph first evaluates), `Join` (equi-join of two data inputs, bilinear delta over per-side hash indexes, residual predicate), `Traverse` (bounded reach over one relationship type, per start element, recomputed only when a visited element or edge changed), `Fixpoint` (bounded unrolling of `distinct(R union step(R))`, so every operator stays incremental; facts needing more than `max` steps are not derived, `maxFacts` is recorded and not enforced), `EmitEntity`, `EmitRelationship`, `Link`. Rules: `readonly` and `bijective` (checked for direction).
- Incremental strategy per operator (`check --plan` prints it): linear via selection vectors and shared columns, per-key accumulators with signed weights, bilinear delta for `Match` and `Series`, per-key state machines for `Threshold`.
- Adapters: Kubernetes list and watch (pods, services, endpoint slices, nodes, events), Hubble flows with lost-event records marking windows `Partial(sourceLoss)`, Azure Resource Graph, Prometheus range queries (one row per sample of every series; the row carries the label set of its series as `series` and the `instance` label when the series has one; a node's rate is the sum over its series of the mean per window), Activity Log (successful operations per resource as telemetry), Azure Monitor platform metrics (CPU, memory, load balancer availability and Event Hubs errors per resource as telemetry), VNet flow logs (one row per tuple; denied and new flows per virtual network and window as telemetry). Each declares its row contracts; activation compares them with the catalog.
- Silence (Def. 7.14 to 7.16, [PROTOCOL.md](PROTOCOL.md) "Version 3.18"): `series G x.p fill 0 within D ttl T` holds 0 for every window in which the source of `p` reported and the element existed, so a covered silence is a record and ends a state; an element without a record for longer than `T` is in no data, which a `Threshold` gives as the value its `nodata then "..."` clause names. The replay and the live input record how far each source has reported (every envelope of an adapter counts for its sources). A window with a loss mark is not covered and holds no fill. The shipped definitions do not use it yet.
- Forwarder markers (`sattle-forwarder` records of [lab/CAPTURE-FORMAT.md](../lab/CAPTURE-FORMAT.md)): a `relist-start` to `relist-end` pair is the complete set of one Kubernetes kind (pods, services, nodes, deployments, endpoint slices): what the engine knows of that kind in the cluster of the marker and the list did not mention is deleted; objects of another cluster stay. A relist that never ends (a crash) deletes nothing. The live input drops an envelope whose key it has seen, except a list record inside a relist: an unchanged object has the same key in every list and still says that it exists. `dropped`, `hubble-reconnect` and `poll-failed` mark the telemetry window that contains them `Partial(forwarderDropped | hubbleReconnect | pollFailed)` (several kinds in one window are joined with `+`), with the dropped count. The live input reads the one hub `sattle-ingest`; the other hubs are read from capture files.
- Event Hubs adapters (read from the `eventhub/sattle-activity` and `sattle-aks` files of a capture, same rows as live would give): `azure.diagnostic-activity` (Activity Log diagnostic records into `ActivityRow`) and `azure.aks-audit` (`kube-audit-admin` records of completed requests into `AuditRow`). Evidence is one element per operation: `ActivityEvent` with `Concerns` to its resource, `WarningEvent` with `About` to its pod, `AuditEvent` (lease renewals left out by the rule), and in the health graph `Evidence` with `EvidenceFor` to the component. The counts stay as telemetry.
- Batch invariance: the state digest does not depend on the chunk size (`dotnet test --filter FullyQualifiedName~BatchInvarianceTests` on the fixtures; the full run adds every capture present at chunk sizes 1, 50 and 100000). The telemetry windows that differed at chunk size 50 had two causes, each a unit test (`BatchInvarianceTests`: two spellings of one resource id in one batch and in two batches in both orders, and a row beyond the late horizon). (1) The Activity Log writes one resource under two spellings of its id (`resourcegroups` and `resourceGroups`); the Group keyed by the raw text made two aggregates for one element and window and the telemetry store keeps the last one written, so the value depended on emission order. The definitions now group by `lowerInvariant(resourceId)`. The premise of the batch-invariance theorem that the input violated: each element and window is written by exactly one group row. (2) A row for a window whose state was already dropped (beyond the late horizon of three widths) created a new window that replaced the value emitted earlier; it is now dropped and counted (`late rows dropped`). `replay` keeps every window revisable by default (`--late-horizon WINDOWS`, default 1,000,000) so history is not dropped; serve and live keep 3.
- Stores: in-memory, SQLite and Cosmos DB for NoSQL behind the six-operation port, one conformance suite parametrized over all three; in-memory telemetry ring behind the telemetry port.
- Cosmos store (`src/Sattle.Cli/CosmosGraphStore.cs`): `sattle replay CAPTURE --store cosmos=ENDPOINT[,db=NAME][,drop]`. Containers `log`, `state`, `identity`, `leases`, hierarchical partition keys led by tenant and graph. The commit point is the creation of the commit record in one transactional batch (a create answers 409 when the revision exists: the conditional write); a commit above the 2 MB limit writes its edits as chunk items `p:{r20}:{i}` first, and the commit record that names them is created last, so it stays the single commit point (chunks without a commit record are not a commit and are overwritten by the retry). Materialization into `state` is idempotent. One writer per graph: a lease item in `leases` (30 s, renewed at half, released on dispose) refuses a second writer even with the right head. Authentication: Entra (`DefaultAzureCredential`) for a real account; the emulator's well-known local key is used only when the endpoint is a loopback address; no key is read from any file. Emulator (vNext preview, http, gateway mode) limits: it supports hierarchical partition keys and transactional batch, and it reports a request charge of 1 per request, so request counts are exact and RU figures are not (`PERF.md`). Materialization writes one transactional batch per logical partition touched by a commit (the version rows and adjacency rows of an entity share a partition; the mirror knows where each version began, so there is no read before the write and a closed interval is replaced by id); a retry after a crash falls back to the idempotent per-edit path. Identity bindings go in one batch per domain partition, and the watermark every 64 commits. The `lens` container of the schema is not created: nothing uses it. Not built: a snapshot above 2 MB per element (an element state is one item).
- Identity merge (Theorem 1.7): the identity of an entity is the smallest id minted for any key that denotes it, whether or not that key was resolved before. When a `Link` binds a key to an entity, the key's own id is a candidate; if it is smaller or the key was already bound to another identity, the loser gets an additive forwarding record, `Rep` follows the chain, bindings stay immutable, and the engine remaps what it emitted under the loser (the master graph gets a patch that moves the loser's relationships to the survivor, the telemetry windows of re-keyed relationships move with them, derived graphs follow through their deltas). The final ids therefore do not depend on the order in which keys are bound (`BatchInvarianceTests`, `IdentityMergeTests`). `sattle replay CAPTURE` prints the `identities:` line (minted, aliased, merged, conflicts); a capture that had `Link` conflicts before the merge has 0 of them now, and the merges are mostly pods whose name key mints a smaller id than their uid.
- Evidence retention (turn 7): evidence elements (`ActivityEvent`, `WarningEvent`, `AuditEvent` and what derives from them) grew without bound; on a capture they are almost all of the master (`sattle replay CAPTURE` prints the master's entity counts by type on the line after `graph master`: add `ActivityEvent`, `WarningEvent` and `AuditEvent` and compare with the entity count). Each evidence rule of `acme.ops` now reads its rows through `|> retain on time for 24h`: an element stays while the logical frontier is less than its event time plus 24 hours. The rule is text in the definitions, the operator is generic, and the retained state is a function of the frontier (tested at chunk sizes 1 to 100000 on the fixtures and on every capture present, `RetentionTests`). To see the effect on a capture, replay it with another age: copy `definitions`, change `retain on time for 24h` to `10m` in `acme.ops.sattle`, run `sattle check --defs COPY --update-pins`, then `sattle replay CAPTURE --defs COPY`, and read the master line again. Not retained: the identity binding table (append-only by Theorem 1.5), the interner, the journal, and the retained input rows of a host. A design alternative that was not taken: a `retain` on the entity type of the ontology, which would have made the engine remove elements by a second mechanism next to the support counts; an operator reuses the retraction that every derived element already follows.
- Serving a capture is a replay: `serve CAPTURE` and `replay CAPTURE` use the same late horizon (1,000,000 windows, `--late-horizon N` for both) and end in the same state digest (`ServeReplayTests`: estate, `lab/fixtures`, the newest capture). Only `serve --live` keeps 3. The horizon is stored with the journal and the seals.
- References: a relationship whose endpoint is not in the graph is served with the endpoint explained (`extent.references` of the snapshot, `danglingBy` of `GET /space`; [PROTOCOL.md](PROTOCOL.md) "Version 3.11"): `inOtherGraph` with the graph named, or `absent` with the key the id was minted from. The health graph takes evidence only for components of the model.
- Lineage: `GET /graphs/{g}/lineage` is complete for lifted elements (every row that supports an element, and every row of a `Group` an element is emitted from, paged), `GET /graphs/{g}/lineage/reverse` answers which higher elements an element is part of, and `replay --out` writes both and the rendered documents ([PROTOCOL.md](PROTOCOL.md) "Version 3.11", `LineageTests`).
- Document projections: a document is a derived graph of `sattle.doc` `Block` entities; one generic renderer gives deterministic Markdown with a digest per revision, served by `GET /graphs/{g}/document` ([PROTOCOL.md](PROTOCOL.md), "Version 3.4"). Worked example: `definitions/acme.report.sattle`, graph `deploymentReport` (a health report over `deploymentHealth`).

## Example 4: the workload model
- `acme.workload` replaces the health model (`acme.health`, `acme.healthmodel`, removed). It answers four questions about one workload (a namespace of a cluster), in two graphs bound in `acme.space`: `workloadStructure` ("what is my workload made of, what does it talk to, and what does each part depend on?") and `workload` ("is my workload healthy, and if not, which part is to blame?"). The workload is two arguments of the binding, `workloadNamespace` and `aksName`.
- **Node types**, all with the label `name`: `Workload`, `Service`, `Deployment`, `Pod`, `Node`, `NodePool`, `Cluster`, `PlatformResource` (an Azure resource the workload uses or runs on: cache, storage account, database server, API Management, private endpoint, virtual network), subtypes of the abstract `Component`; `Signal` (one per component and authored rule) and `DependencyEvidence` (one per dependency and way it was found).
- **Three kinds of edges**, kept apart by their declared kind (PROTOCOL.md, 3.17): communication `TalksTo` (lifted from pod flows, with flows and drops per window); composition `Contains` (a hierarchy: workload, service, deployment, pod), `RunsOn`, `MemberOf` (node, pool, cluster), `BackedBy` (an ExternalName Service and the server it names), `ConnectedThrough` (a resource, its private endpoint, its virtual network); dependency `DependsOn` and `Exposes` (a gateway needs its backend). `Affects` is the roll-up edge, made from dependency and composition, never from communication; `EvidenceFor` and `Measures` are support.
- **Six ways a dependency is found**, each kept as `DependencyEvidence` whose lineage names the master facts: (1) a pod's flows to the address of a private endpoint (Hubble `IP.destination`, Resource Graph private endpoint properties); (2) the name Hubble resolved for the flow's address (`destination_names`, by the name suffix of the resource type); (3) the workload identity of the pod's service account (ServiceAccount annotation `azure.workload.identity/client-id`, the identity's client and principal id, a role assignment's principal and scope); (4) an environment variable of the Deployment that names a host (`*HOST`, `*URL`, ... only: other values may be secrets); (5) pods of one service calling pods of another; (6) an API Management backend whose host is a Service's address. A dependency on a resource that a Service stands for (an ExternalName Service) is a dependency on that Service.
- **Health.** A signal is a meter read against an authored rule (`SignalRule` records: type, meter, thresholds, severity, inverted or not): Azure Monitor metrics of resources and Prometheus meters of nodes with a time to live of five minutes, and a pod's warning events with `fill 0` (a minute in which the Kubernetes source reported without a warning is a 0). Severity 0 healthy, 1 no data, 2 degraded, 3 unhealthy. A pod counts the node it runs on; a deployment is unhealthy only when at least half of its pods are (degraded when at least half are degraded or worse). Every component's state is the worst severity over what affects it, up to sixteen edges (`traverse ... via Affects`); a component that nothing measured is Unknown.
- **On the estate** (`tests/Sattle.Tests/fixtures/estate`, five scenarios on a 24-minute timeline, `WorkloadTests`): A, the cache overloaded: the cache, web and the workload Degraded, api Healthy; C, one of three web pods crash-looping: the pod Unhealthy, its deployment and web Healthy; B, the database down: the server, the database Service, api, web, API Management and the workload Unhealthy, the cache and the storage account Healthy; D, API Management failing: it is Unhealthy, api behind it is not; E, the storage account's metrics stopping: it and web and the workload "No data".
- **On the real captures** (`lab/captures`, local overlay): the structure (workload, services, deployments, pods, nodes, pools, cluster) and the dependencies between services from their calls; the other five ways find nothing, because the Resource Graph rows carry no `properties`, no service account names a workload identity and no environment variable names a resource there; with no authored signal rules every state is Unknown.

## Edge lifting: a projection is an abstraction of the graph below it, edges included
- **Definition.** A level maps the nodes of the graph below to nodes of its own, the image `f(n)`: a pod to its service, a service to the capability that realizes it. The edges of the level are the quotient of the edges below: for every edge `a -> b` below with images on both ends, the level has the edge `f(a) -> f(b)`. Nodes and edges are lifted together, so a level never has nodes that the edges below cannot reach.
- **Self-loops** (`f(a) == f(b)`): not lifted. Traffic inside one image is not a dependency between images.
- **Parallel edges** (several edges below with the same pair of images): one edge, key `f(a) -> f(b)`. Its counters are summed (`sum` over the windows of all edges below), a ratio is recomputed from the sums and never summed or averaged, and a state is derived again from the aggregate by the same threshold, so the state of the lifted edge is the state of the traffic it carries, not the worst of its parts.
- **A node with several images** (a service that realizes two capabilities): `Realizes` is declared 0 .. 1 per source, so the ontology flags it, and the lift states a policy: the node is not lifted (nothing is counted for two images). Chosen over splitting (fractional counts) and a first-by-order pick (order is not defined on handles); a pod that backs two services is the one exception, it counts for each (`Backs` is not a function). Tests: `A_service_with_two_images_is_not_lifted_the_declared_cardinality_reports_it_and_no_call_is_counted_twice`.
- **Composition.** Two lifts equal the one-step lift from the bottom (`The_composition_of_two_lifts_gives_the_same_edges_and_sums_as_the_one_step_lift_from_the_pods`), and the ratio and state of a lifted edge are those of the summed counts (`The_ratio_of_a_lifted_edge_is_recomputed_from_the_summed_counts_and_its_state_follows_the_aggregate`).
- **Ends without an image** (a service that realizes no capability, a retired capability): the edge is not lifted. The inner join drops it; nothing is invented, and there is no catch-all node.
- **The statement.** One `lift` per level, in a forward projection or in a readonly rule:
  ```
  lift NAME as REL from GRAPH EDGETYPE via GRAPH MAPPING
    [when image.p == v]  [carry p = q, ...]  [keep c = src.p, ...]  [derive p = expr, ...]
    [state p of m above A for N then "x" below B for M then "y" initial "z"]
    [images reject|each]  [selfloops keep]  [within 24h];
  ```
  `GRAPH EDGETYPE` is the relationship type of the lower graph that is lifted (a graph port of the projection), `GRAPH MAPPING` the relationship type that gives each lower node its image (the target of the mapping is the image, the nodes of the two graphs are matched by identity: the same id, `entityId(x) == entityId(y)`), `REL` the relationship type of this projection's output ontology that comes out, keyed by `NAME`.
- **As it stands in the service tree** (pods to services; a pod that backs two services counts for both):
  ```
  lift dependsOn as DependsOn from master infra.Calls via master infra.Backs
    keep cluster = src.cluster, namespace = src.namespace
    derive dropRatio = if(flows > 0, drops / flows, 0.0), flowRate = rate(flows)
    state status of dropRatio above 0.05 for 3 then "degraded" below 0.02 for 3 then "ok" initial "ok"
    images each;
  ```
  and in the capability level (services to capabilities, from the service tree; `Realizes` is declared a function, so no `images` clause):
  ```
  lift dependsOn as DependsOn from tree svc.DependsOn via master ops.Realizes
    when image.status != "retired"
    carry callFlows = flows, callDrops = drops
    derive callDropRatio = if(callFlows > 0, callDrops / callFlows, 0.0)
    state callStatus of callDropRatio above 0.05 for 3 then "degraded" below 0.02 for 3 then "ok" initial "ok";
  ```
- **What the defaults are, and the clause that changes each.** Telemetry properties of `REL` that the lower relationship also has (same name, same kind) are carried with the combine rule the property declares (`sum`, `min`, `max`, `mean`); `carry p = q` carries `q` into `p` (another name), `derive` computes a property from the carried ones per window (`rate`, ratios), `state` runs a threshold with hysteresis over one of them and sets a state property, `keep c = src.p` (or `dst.p`) keeps a data property of the source or target image on the windows (so that a later `rollup` can group by it). `when` restricts the images. Self-loops are dropped (`selfloops keep` emits them). A node with several images is not lifted (`images reject`, the default) or counts for each (`images each`); without the clause the mapping must be declared `constraint cardinality M per source 0 .. 1`. `within` is the look-back of the series (default 24 h). The relation `NAME` (columns `src`, `dst`, `windowStart`, the kept, carried and derived properties) can be read by later statements: `let serviceOut = dependsOn |> rollup by { s: src } combine { flowsOut: sum(flows) };`.
- **A node of the definition graph.** The catalog keeps one `Lift` operator per statement (kernel type `Lift` with the slots `carry`, `keep`, `when`, `derive`, `state` and the ports `edges`, `map`, `out`; PROTOCOL.md "Version 3.13"), the printer prints it back, `/palette` lists it. The planner lowers it when the projection is checked: in a copy of the graph the Lift node is replaced by the operators it stands for, `Match` of the edges and of the mapping, `Group` and `Join` for the images, `Filter` for the self-loops, `Series`, `Rollup`, `Map`, `Threshold`, and the create and update emits of `REL` (`dependsOn.emit.1` to `3`), generated as text, parsed and lowered by the ordinary front end. Every strategy, batch invariance, retention and the lineage of those operators therefore apply as they are: a lifted edge names every lower edge it stands for (roles `edge`, `source`, `target`, `sourceMapped`, `targetMapped`, `sourceImage`, `targetImage`), forward and reverse. `sattle check --plan` lists the statement and the operators it was lowered to (`dependsOn: Lift Calls through Backs to DependsOn (images each), lowered to 15 operators: ...`).
- **What the checker refuses**, naming the statement (`lift dependsOn: ...`): a mapping that is neither declared a function nor given an `images` policy, a type that is not in the ontology of its graph (the edge or mapping type) or of the output (the lifted type), a `carry` whose target or source is not a telemetry property or whose kinds differ, a combine rule that is not sum, min, max or mean, a `derive` target that is not telemetry, a `state` that names a measure or something that is neither carried nor derived, a `keep` that is not `src.p` or `dst.p` of a data property of the image, `derive` or `state` without telemetry, a lift in a lens or bijective rule (its edges cannot be edited back), and whatever the generated operators fail to check (an unknown column in a `derive`).
- **What the statement does not do.** It lifts the edges; the nodes of the level are emitted by ordinary `emit entity` statements (a service tree may hold services that no pod backs, a level may hold capabilities that realize no service), and their counts by `emit update`.
- **Size.** The dependency part of `serviceDeps` went from 24 lines to 11 (the projection from 43 to 30), the rule `lifted` of `capabilityView` from 22 lines to 7.
- **Tests.** `LiftTests`: the lift statements give the graphs and telemetry of the hand-written modules kept under `tests/Sattle.Tests/fixtures/handwritten` (estate, `lab/fixtures`, the newest capture), chunk sizes 1, 50 and 100000, conservation, every clause, the printer round trip, the refusals; `DraftTests` (palette entry, skeleton, draft edit and preview of a lift), `RefactorTests` (a rule with a lift moves between stacked projections, the lift alone cannot be extracted away from its readers), `LineageTests`.
- **Example (estate).** Pods and their `Calls` in the master; `serviceTree`: services with `DependsOn` web to api and api to db (flows, drops, ratio, state); `capabilities`: Storefront, Ordering, Data platform with `DependsOn` Storefront to Ordering and Ordering to Data platform, `callFlows` equal to the service-level `flows`, under the `Under` hierarchy (Commerce above Storefront and Ordering).
- **Authored capabilities in a capture.** Envelopes of source `authoring` (`tests/Sattle.Tests/fixtures/estate/authoring/capabilities.ndjson`): payload `{ "kind": "capability", "capId", "name", "owner", "status", "parentId"? }` (a later row with the same `capId` revises it, status `retired` retires it) or `{ "kind": "realizes", "capId", "cluster", "namespace", "service" }`. Rows that miss a field are rejected and counted.
- **Tests.** `ProjectionEdgesTests` (the properties, written before the statement and unchanged by it): every graph of the space whose output ontology declares relationship types has relationships on the estate (exemptions, with reasons: the two reports and `treeSignals`); the lifted flows equal the service flows; the policies (self-loop, parallel edges, no image, retired capability) on variants of the estate; the static space written by `replay --out` has the edges in the final snapshot and the patches.

## Health tree of the estate (engine turn 14)
- **What it is.** `healthTree` is a tree over everything in the master that can have health, derived from the data with no names in the definitions (`acme.tree`, `acme.treehealth`, `acme.treereport`). Azure side: subscription, resource group, resource, from the resource ids Resource Graph gives. Kubernetes side: cluster, namespace, workload (Deployment), pod, node. A cluster that is an Azure resource is one element: the cluster of a Kubernetes label is the Azure resource that is the parent of the machines its nodes run on (`Node.resourceId` to the VM, whose `parentId` is the AKS resource), else an element of its own; the namespaces, the nodes and the workloads hang below it. Every element has exactly one parent (`constraint cardinality Contains per target 0 .. 1`, the roots have none, checked by `Conformance` like `Realizes`), dependencies are separate relationship types and never parents.
- **Graphs** (all in `acme.space`): `treeStructure` (elements and `Contains`), `treeSignals` (one `Signal` per element and rule), `treeRollup` (the policy of each element and the `Rolls` edges the roll-up follows), `healthTree` (the elements with own state, rolled-up state, counts, curation flags, and the evidence), `healthReport` (a Markdown document). `Element` has `nodeKey`, `nodeKind` (subscription, resourceGroup, resource, cluster, namespace, workload, pod, node), `nodeName`, `ownSeverity`/`ownState`, `rolledSeverity`/`rolledState` (`Healthy`, `Degraded`, `Unhealthy`, `Unknown`, value roles ok, warning, danger, unknown), `healthyCount`, `degradedCount`, `unhealthyCount`, `monitored` (the counts of the elements at and below it that carry signals), `critical`, `hidden`, `curatedBy`, `rollupMode`, `rollupShare`; `Signal` entities hang on their element by `Measures` with a streamed `signalValue`. The property names are unique in the catalog on purpose: a name two modules declare is served qualified and would change the wire names of existing graphs. The ontology endpoint serves `treeState` (the role of each tree property) per entity type. `Contains` is declared `hierarchy` in the ontology (`relationship Contains (Element) -> (Element) hierarchy`, served as `hierarchy: true` by the ontology endpoint): a viewer draws any graph with such a relationship as a tree.
- **Signals are data.** The master has one `Meter` entity per series (an Azure Monitor metric of a resource, a Prometheus metric of a node, the warning events of a pod, `MeterOf` to the element) and authored `SignalRule` records (source `authoring`, kind `signalRule`: `id`, `type` (an Azure resource type in lower case, `node`, `pod`, or `*`), `meter`, `above`, `enterAfter`, `below`, `exitAfter`, `severity` 1 or 2, `invert`). `treeSignals` joins the two and runs a `Threshold` whose parameters are read from the rule row (`threshold v by {...} above above for enterAfter then "on" below below for exitAfter then "off" ...`: a new language form, the four parameters may be expressions over the columns of the row). A new signal kind, a changed threshold or severity is a record; no statement changes (`HealthTreeTests`).
- **Roll-up.** The own state of an element is its worst signal that is on. The rolled-up state follows the element's policy (authored record `policy`: `id` = element key or kind, `mode` = `worst` (the default), `share` (Unhealthy when the share of the monitored elements below it that are Unhealthy is above `share`, Degraded when any is not healthy) or `ignore` (the element keeps its own state and what is below it does not reach it or its ancestors)). Honest limits: the roll-up reads everything below an element that the `Rolls` edges reach, not only the direct children, so `share` is a share of the monitored elements below the element and an ancestor with the default policy still sees the elements below a `share` element; `ignore` is exact because it cuts the `Rolls` edges. Impact along dependency edges is not built (the lifted `DependsOn` of the service tree and the capabilities exist beside the tree).
- **Curation is data** (authoring kind `curation`: `id`, `action`, `target` = an element key, `value`): `group` (the target becomes a child of the root workload named by `value`), `move` (the target's parent is the element key in `value`), `hide` (the target and everything below it leave the roll-up, `hidden`), `critical` (`critical: true`). Without any record the full default tree comes out. Not built: a threshold override for one element beyond adding a rule with the element key (rules match a type or `*`).
- **Evidence** hangs on the element it concerns (`Evidence`, `EvidenceFor (Evidence) -> (Element)`): warning events on pods and Activity Log operations on resources, with the lineage of an evidence element naming the master event. `healthReport` renders the totals per state and the elements that are not healthy, worst first.
- **The workload model (`acme.workload`, Example 4) and the tree.** The model names its workload as arguments and rolls up along dependency and composition; the tree has no names and rolls up along containment only. Both read the same authored rules and meters and agree where both measure the same way (the cluster and the nodes, `The_workload_model_and_the_tree_agree_on_the_state_of_what_both_measure_the_same_way`). They differ where the model reads silence: the tree has no fill and no time to live, so on the estate its crash-looping pod keeps its last state after scenario C and it does not see that the storage account stopped reporting (scenario E). The tree stays paused; taking fill and time to live into it is the open piece.
- **Data.** `tests/Sattle.Tests/fixtures/estate-wide` (written by `build-estate-wide.py`, invented names): 3 subscriptions, 8 resource groups, 2 clusters (the Kubernetes records of a capture name their cluster in the envelope meta), 6 namespaces, 12 workloads, 24 pods, 4 nodes, failures at four depths (a pod, a node, a cluster, an Event Hubs namespace).
- **Tests.** `HealthTreeTests` (27 cases): the tree property on four captures, one element per cluster, the default tree without records, roll-up over three levels per policy, the counts, every kind of curation record and its removal, rule rows added and changed, the printed threshold, the ontology marker and value roles, evidence, the report, chunk sizes 1, 50 and 100000, incrementality (one pod: only its path changes), lineage, restart from a store.

## Deviations from the research documents
- **Revisions and wire**: as accepted in research 01. Integers on the wire are strings. Instants are nanoseconds in a signed 64-bit integer (1678 to 2262), decimals are .NET `decimal` (28 digits), not unbounded.
- **Module version**: `module m @ 1.0.0;` takes an optional version (default 1.0.0) because the grammar has no place for a release version.
- **Kernel**: `Correspondence.source` and `.target` are named `sourceRefs` and `targetRefs`, because section 2.3 gives them kind `L<T>` while `Assign.target` is `T` and one property name keeps one kind per module. Canonicalizers `LowerInvariant` and `Trim` are separate function nodes (`canon.LowerInvariant`) from the scalar functions of the same name. A `NoType` relationship type and `NoType` entity type exist in `K`. Single-child slots use the segment `slot:#0`.
- **`was`**: keeps the old id; references still use the id segment (old name).
- **Release digest**: formula of section 2.9. Adapters declare a row-contract shape, not a digest, so a definition change needs no rebuild; activation compares shapes.
- **Identity**: no `Key`, `Identity` or `Evidence` graph nodes. Bindings are an append-only table in the identity catalog, written with the commit of the master graph (SQLite `identity_binding`). Two identities are merged by an additive forwarding record (see "What exists"); a `Link` conflict is now only a key already bound to an identity of a different type. Entity ids are `e:` plus 26 base32 characters of SHA-256 over the JCS of `[tenant, domain, component encodings]`. Relationship ids hash `[tenant, output ontology module, key rule, source id, target id]`.
- **Telemetry**: windows are closed inside the projection by `Group` over `Window` and by the explicit frontier. Closed-window records are not recorded as separate inputs (Def. 7.7); replay recomputes them from the raw rows, which is deterministic. The port gains `MarkPartial` and a `Deleted` flag on samples (window retraction), both on the ingest side.
- **Storage port** is synchronous. Identity bindings and the frontier travel in the commit batch as specified; `Follow` returns a list, not a stream.
- **Property tests**: seeded generators in xunit theories, 4,000 generated cases per property of Theorems 4.1 to 4.8 and the Ch. 3 invariants, not FsCheck (one dependency fewer, same reproducibility by seed).
- **Benchmark**: Stopwatch and GC counters, not BenchmarkDotNet. No IL or delegate compiler: only the vectorized interpreter exists.
- **Fusion** is by selection vectors and shared column arrays, not generated code.
- **Late data**: closed windows stay revisable for 3 window widths (`EngineOptions.LateHorizonWindows`), then their state is dropped.
- **Columns after aggregation**: `v.p` read columns are not carried past `Group`, `Rollup` or `Threshold`; reading one there is a type error. Property reads must happen before grouping.

## Not done, or not verified
- Not built: `sync` rules, `Delta`. `--live` reads one hub (`sattle-ingest`) of one partition; the `eventhub/` capture files mirror the direct sources and are skipped by `replay`.
- Adapters: all sources the captures carry have an adapter, including the AKS audit and Activity Log diagnostic records from Event Hubs and the forwarder's own `sattle-forwarder` records. What is missing is the live input: `--live` reads the one hub `sattle-ingest`; `sattle-aks` and `sattle-activity` are read from capture files only.
- Operators missing: `Delta` (no property in the definitions or captures is cumulative, so it would ship without data to test against) and rule class `sync` (triple graph grammar rules need the stored correspondence graph and the FWD and BWD translators of [Ch. 8](../paper/ch08-sync-direction-and-bidirectional-consistency.md), none of which exist); `Union` conflict policies `requireEqual`, `preferFirst`, `preferLast` (rows have no key). Both stay `supported: false` in `/palette` with the reason. They parse or check to a typed error with a position.
- Q5 (pod name reuse) was not evaluated; a flow that names a pod before the pod row arrives mints a provisional identity and the pod row then merges it.
- Whole-engine memory at the 240,000-pair estate is far over the hot graph's (`sattle bench estate` prints both: heap after structure and at the end, against the hot graph's `sattle bench` memory line); H5, H7, H8, H10 are measured in `PERF.md` with what each still needs on real hardware.
- Event time of Hubble flows is not monotone (the capture starts with history); late rows revise their windows, covered by a test, and the real capture produced no dropped or rejected rows.
- The canvas was not run against the exported files or the protocol; both were validated against the schemas the canvas uses. The WebSocket and HTTP endpoints were exercised with curl and Node's WebSocket client, not with the canvas.
