# Where the shop architecture comes from

The storefront, checkout, warehouse, support and reporting software follow a published retail architecture. Order **O-104** and return **R-104** are fictional. The master graph contains software, API boundaries and digital records. For example, a shipment appears as a request to the carrier API and a scan event sent to the tracking service. [Retail architecture](https://learn.microsoft.com/en-us/dynamics365/commerce/dev-itpro/commerce-architecture)

| System | Published design | Records for order O-104 |
| --- | --- | --- |
| Orders and logistics | The checkout service handles purchases for the storefront. The supply chain systems track stock, warehouse work and transportation. [Architecture overview](https://learn.microsoft.com/en-us/dynamics365/commerce/dev-itpro/commerce-architecture) | The order system writes a reservation to the stock ledger. The warehouse API requests a shipment from the carrier API. A later scan event changes the expected delivery date. |
| Returns | A return record connects order lines to a receipt scan, an inspection result and a credit decision. [Sales returns](https://learn.microsoft.com/en-us/dynamics365/supply-chain/sales-marketing/sales-returns) | Return R-104 references two lines on order O-104. The inspection log marks one line for restocking and one for scrap. The approval record says how much the refund job can pay. |
| CRM | Customer support and the order system can share order and customer records. [Back-office integration](https://learn.microsoft.com/en-us/dynamics365/commerce/dev-itpro/commerce-architecture) | The tracking service updates the support case with the carrier’s delay. The case links back to O-104. |
| Marketing | An Azure Function reads order events and checks their IDs in Cosmos DB. Service Bus carries each new event to a workflow in Logic Apps, which passes it to the marketing tool. [Published integration and diagram](https://learn.microsoft.com/en-us/dynamics365/guidance/resources/data-integration-commerce-customer-insights-journeys) | An order event triggers a consent check. The consent record blocks promotional email. The shipping request in the warehouse API stays open. [Consent controls](https://learn.microsoft.com/en-us/dynamics365/customer-insights/journeys/real-time-marketing-compliance-settings) |
| Analytics | A data lake can combine back-office records with online sales data. [Retail analytics](https://learn.microsoft.com/en-us/dynamics365/commerce/dev-itpro/commerce-architecture) | The report matches the booked sale, delivery and settled refund. The report deducts the refund when the payment receipt arrives. |

## How the shop handles a return

A message about return R-104 reaches a support agent. Later, a queued message starts a background review of the same case. Both agents run in Microsoft Foundry. The support agent can request an order lookup. The shop application runs it. A Python sandbox totals the receipt lines, and the application saves the result to Blob Storage. The refund job is a background program. It reads the approval and calls the external payment API. A scheduled job compares each receipt with the entry in the merchant’s ledger. ## From shop records to a health model

The shop’s first master graph has 46 entities and 68 typed relationships. A projection groups the software and its records into 14 capabilities. It keeps 32 links within their groups. The other 36 become 35 typed links between capabilities. Some connect the same pair of capabilities in the same direction. The diagram draws one arrow per pair, 30 in all. For instance, the refund job reads the case store and requires an approval record. Both records support the business-level link from **Payout** to **Returns intake**. The tree shows which original links support that dependency. [Shop graph](case.js) · [Projection](projection.js) · [White paper, chapter 5.8](../../../paper/ch05-projection-language.md#58-levels-of-abstraction-a-projection-lifts-the-edges-with-the-nodes)

The ontology defines the kinds of links the graph can express, such as “reads” and “requires”. Health rules use those links and observations to assign a state. For example, a timeout on a required payment call can block a refund while the support agent can still look up the order. People can maintain the ontology and refine the rules. The retail states come from this example. Azure inventory can identify a storage account. A timeout at an external API comes from the shop’s call log. The provider’s internal health stays unknown without readings from the provider. The pg-shop states come from a Sattle engine run against recorded inputs.
